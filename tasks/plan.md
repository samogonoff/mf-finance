# PLAN — ВГО-отчёт на `Table_Fin_PL`

> Источник требований: `SPEC.md` (корень репо). Режим: план, без правок кода.
> Дата: 2026-06-24. Ветка: `add-action`.

---

## 1. Что меняем (в одном абзаце)

Отчёт «Задолженность ВГО» получает новый первоисточник — каноническую месячную
ОПУ-витрину `FinDWH.dbo.Table_Fin_PL` (наполняется `Update_Table_Fin_PL`). Из неё берём
**выручку/обороты, признак ВГО, страну, компанию/контрагента**; **сальдо ДЗ/КЗ, договор,
срок/просрочку, ИНН/менеджер/канал** дотягиваем из `Premaster1C` (fallback-цепочка).
Новый источник `DEBT_BACKEND=finpl` становится дефолтным. Гранулярность — месячная.

## 3. Принцип нарезки — вертикальные срезы

Каждая задача даёт **один сквозной работающий путь**, а не горизонтальный слой:

- **T4** уже отдаёт реальный ответ `/report` (только выручка) через `DEBT_BACKEND=finpl` —
  это законченный, проверяемый срез, даже без ДЗ/КЗ.
- **T7** добавляет второй измеритель (ДЗ/КЗ из Premaster) поверх рабочего среза.
- **T8** добавляет drilldown. **T9** — переключение дефолта.

Так на каждом чекпоинте есть демонстрируемый результат и возможность отката
(`DEBT_BACKEND=mssql` возвращает старое поведение вплоть до T9).

## 4. Ключевые проектные решения (зафиксировать в коде/доках)

1. **Матчинг компании** (T1): `Table_Fin_PL.Компания` (код) → ИНН через статичный map.
   Контрагент — по `[ВГО]=1` + `CounterpartyName`; PartnerINN дотягивается из Premaster.
2. **ВГО-фильтр** (T3): `WHERE [ВГО]=1` заменяет `vgoMSSQLClause`; включает DR/DR2/GP.
3. **Мультивалюта** (T4): `Table_Fin_PL` хранит 4 суммы (BYN/нац/USD/RUB) в одной строке.
   Решить, разворачивать ли в 4 валютные строки или брать функц. валюту юрлица
   (как `CurrencyForCountry` сейчас). → дизайн-заметка в T4.
4. **Выручка** (T4): из `Amount*` по строкам, где `GroupPL`/`CodePL` относятся к продажам.
   Свериться с текущей классификацией `KindRevenue` (оверлей `[002 CodePL]`).
5. **Грань merge** (T7, РИСК): выручка — на уровне (Компания, Контрагент, Валюта);
   ДЗ/КЗ — на уровне (Компания, Контрагент, Счёт, Договор, Валюта). Решить:
   (a) отдельные строки (UI группирует), или (b) revenue-aggregate на пару. → CHECKPOINT B.
6. **Период** (T4): месячная нормализация `date_from/date_to`, клампинг нижней границы 2025-01.

## 5. Чекпоинты (точки человеческого ревью)

- **CHECKPOINT A** (после T6): сквозной revenue-путь из `Table_Fin_PL` работает (opt-in).
  Проверяем форму строк, классификацию выручки, мультивалюту на 1–2 месяцах.
- **CHECKPOINT B** (после T7): ревью **грануляр-merge** ДЗ/КЗ + выручка (риск §11.2 SPEC).
  Согласовать с заказчиком: отдельные строки vs агрегат; на какую дату closing-сальдо.
- **CHECKPOINT C** (после T9): финальная сверка сумм ВГО с «официальным» PL-файлом
  (финотдел), готовность prod (Table_Fin_PL наполнена), смена дефолта `DEBT_BACKEND`.

## 6. Риски и развязки

| Риск | Митигиация |
|---|---|
| `Table_Fin_PL` пуста в dev-снэпшоте | Все срезы проверяемы через mock (T5); live-проверка — на prod-данных |
| Грануляр-mismatch выручка/сальдо (§11.2) | Отдельная задача T7 + CHECKPOINT B до cutover |
| Смена дефолта ломает prod при пустой таблице | T9 последняя, с чек-листом «таблица наполнена»; откат `DEBT_BACKEND=mssql` |
| `GP`(190465888) — имя/страна неизвестны | Уточнить у заказчика (SPEC §11.1) до T1-финализации; временно код без имени |
| ВГО-контрагент с ИНН=NULL (Летникова) | T7: PartnerINN допускает пустое; не падать |
| `CounterpartyName`→`Counterparty1C` ненадёжно по имени | T7: PartnerINN/менеджер best-effort, fallback на имя из Table_Fin_PL |
