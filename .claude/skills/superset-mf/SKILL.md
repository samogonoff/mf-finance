# Superset в Finance Cabinet

Дополняет скиллы `preset-mcp-skills` / `preset-api-skills` проектной спецификой.
Те описывают, КАК устроены инструменты; этот — ЧТО у нас за данные и какие
здесь правила. При конфликте побеждает этот файл.

## Где что лежит

| Что | Путь |
|---|---|
| Контур | `swarm/docker-compose.superset.yml` |
| Конфиг Superset | `swarm/superset/superset_config.py` |
| Образ (драйверы) | `swarm/superset/Dockerfile` |
| Ассеты в git | `swarm/superset/assets/` |
| Скрипт синхронизации | `swarm/superset/assets_sync.py` |
| Команды | `swarm/Makefile`, префикс `superset-` |

UI: `http://localhost:8093` · MCP: `http://localhost:5008/mcp`

## Главное правило: метабаза производна от git

Дашборды, чарты и датасеты Superset хранятся в его метабазе Postgres. **Правка
только в UI = правка, которой нет в git и не будет на проде.**

Любое изменение обязано закончиться экспортом:

```bash
cd swarm && make superset-assets-export
git -C .. diff -- swarm/superset/assets/
```

Обратное направление (накатить git-состояние в свой инстанс):

```bash
cd swarm && make superset-assets-import
```

Импорт идёт через `/api/v1/assets/import/` (ImportAssetsCommand), сопоставление
объектов **по uuid**. Не через `superset import-directory`: тот использует
ImportExamplesCommand, который транспилирует SQL виртуальных датасетов под
целевой диалект и тихо портит наши ClickHouse-запросы.

### UUID подключений менять нельзя

`assets/databases/*.yaml` содержат зашитые руками uuid. Датасеты ссылаются на
подключение именно по нему, и это единственное, что связывает dev и prod. Смена
uuid = на проде появится второе подключение, а датасеты останутся на старом.

Если подключение создано **в UI**, его в git нет — `make superset-assets-export`
про это предупредит в stderr. Опиши его в `assets/databases/` руками:
`${ПЛЕЙСХОЛДЕР}` в `sqlalchemy_uri` + новый постоянный uuid.

### Секреты

В git — только `${VAR}`-плейсхолдеры. Строки соединения приходят из окружения
при импорте. Никогда не коммить `sqlalchemy_uri` с реальным паролем и не
подставлять пароли в YAML «на время отладки».

## Источники данных

| Подключение | Что внутри | Осторожно |
|---|---|---|
| **MF ClickHouse (finance)** | `fact_glmf`, `fact_findebt`, `fact_findebt_ccy`, `debt_facts`, `turnover_facts`, `currency_daily`, `dim_contract` | Основное место для тяжёлых свёрток. Схема — `clickhouse/migrations/*.up.sql` |
| **MF Postgres (finance)** | Тактические планы (P&L), справочники ЦФО/ЦЗ, пользователи, уведомления, баг-трекер | Живая операционная БД Go-API. Только чтение |
| **MF Postgres (cost)** | Калькуляции себестоимости, согласования ПЭО, история цен | Живая БД раздела. Только чтение |
| **MF MSSQL (OLAP/Premaster)** | `[Payments].[report].[FinDebt1/3]` (10.10.6.15), Premaster1C и `FinDWH.dbo.Table_Fin_PL` (10.10.6.107) | **Требует VPN.** Живой OLAP корпоративного контура — тяжёлые запросы здесь бьют по чужой работе |

Во всех подключениях `allow_dml: false`, `allow_ctas/cvas: false`. Superset —
читатель. Если задача требует записи, это не задача для Superset.

### Куда идти за цифрами

- Задолженность ВГО, выручка, ДЗ/КЗ → ClickHouse `fact_glmf` / `fact_findebt`.
  Методология и расхождения методов — `SPEC.md` и `docs/reports/debt/`.
- Себестоимость, маржа, согласования → Postgres `cost`. Смысл полей —
  `python/cost/AGENTS.md`.
- Тактические планы → Postgres `finance`, `docs/reports/plans/SPEC.md`.
- MSSQL — только разведка и сверка с первоисточником, не витрина для дашбордов.

## Гранулярность cost_data_cache — читать перед любым агрегатом

`cost_data_cache` (≈1 млн строк) — это **построчная детализация материалов и
операций**, а не калькуляции. Себестоимость модели повторяется на каждой строке
материала, поэтому `SUM("Себестоимость, руб.")` по таблице завышает результат
примерно в 11 раз.

Натуральный ключ калькуляции:

```
Модель + Артикул + Признак калькуляции + PLAN_ID + дата расчета
      + Номер задания производства
```

**Номер задания производства входит в ключ** — подтверждено заказчиком
12.08.2026: одна модель в разных заданиях производства может иметь разную
себестоимость. Без него расхождения в 12 396 ключах из 28 340; с ним — 3.

С этим ключом: 86 748 калькуляций на 4 238 моделей, ~11,5 строк материалов на
каждую. Любой агрегат по себестоимости или цене строится поверх дедупликации до
этого уровня, а не по сырой таблице.

`Уровень цен` и `color` в ключ НЕ входят — проверял, не помогают.

## Особенности MCP-инструментов Superset (проверено 12.08.2026)

Всё это стоило времени, поэтому записано:

- **Обёртка `request` нужна не всем.** `execute_sql`, `generate_chart`,
  `create_virtual_dataset` ждут `{"request": {...}}`. А `get_chart_type_schema`
  принимает аргументы **плоско**. Ошибка выглядит как «Unexpected keyword
  argument request».
- **`generate_chart` по умолчанию НЕ сохраняет чарт.** `save_chart: false` —
  дефолт, хотя описание инструмента обещает «create and save permanently».
  Без флага получите `chart: null` и `success: true`. Проверять через
  `list_charts`.
- **`create_virtual_dataset` ждёт `dataset_name`**, не `table_name`.
- **`generate_dashboard` игнорирует имя** — заголовок склеивается из имён
  чартов. Переименовывать через `PUT /api/v1/dashboard/{id}`.
- **Postgres-движок не компилирует агрегат `MEDIAN`**, хотя он есть в enum
  схемы чарта. Падает на compile с `'MEDIAN'`. Для медиан считайте
  `percentile_cont` в SQL витрины и берите значение агрегатом `MAX` —
  одна строка на группу.
- **Валидные `chart_type`:** `big_number`, `handlebars`, `mixed_timeseries`,
  `pie`, `pivot_table`, `table`, `xy`. Столбчатая диаграмма — это
  `xy` + `kind: "bar"`, никакого `"bar"` отдельно нет.
- **Чёрный список SQL-функций ловит имена таблиц.** Запрос с
  `cost_calc_versions` / `cost_calc_version_rows` отбивается с «Disallowed SQL
  functions: version».
- Ошибки MCP отдают только `Error ID`. Расшифровка — в логах:
  `docker logs swarm-superset-mcp-1`, искать по этому id.

## Конвенция имён: латинский слаг в начале

Superset делает имя файла экспорта из названия объекта, выбрасывая кириллицу —
«Себестоимость по этапам» превращается в `2.yaml`, `4_3.yaml`, `BYN_1.yaml`.
Ревью по `git diff` при таких именах невозможно.

Поэтому названия чартов и дашбордов начинаем с латинского слага:

```
cost-stage-median · Себестоимость по этапам калькулирования (медиана, BYN)
→ charts/cost-stage-median__BYN_1.yaml
```

Числовой суффикс добавляет сам Superset, его не убрать. Идентичность объекта
всё равно держится на `uuid` внутри файла, а не на имени файла: **переименование
объекта в git выглядит как удаление + добавление**, хотя объект тот же.

## Правила запросов

- Виртуальные датасеты предпочитай вьюхам в БД: витрина описана в git-YAML,
  а не в чужой миграции. Исключение — если логика нужна и другим сервисам.
- В ClickHouse всегда ограничивай период (`DateOfLoad`, `date`) — таблицы
  фактов растут и полный скан бьёт по памяти.
- Дефолтный `ROW_LIMIT` 50k, потолок SQL Lab 100k. Нужно больше — это выгрузка,
  а не дашборд.
- Числа в дашбордах — денежные, формат с разделителями разрядов и явной
  валютой (BYN/USD). В отчётах ВГО валюта существенна: суммы пересчитываются
  через `currency_daily` на дату документа.

## Границы правок

Раздел «Себестоимость» правится **только внутри `python/cost/`** — это правило
из `python/cost/AGENTS.md`, заказчик его проверяет. Superset-контур живёт в
`swarm/` и на это правило не влияет, но: если задача про дашборд по
себестоимости требует нового поля из API раздела — правка API идёт в
`python/cost/`, отдельным изменением, и стейджится поимённо.

В рабочем дереве постоянно висят чужие незакоммиченные изменения. `git add -A`
здесь опасен — добавляй файлы по именам.

## Прод

Прод-выкатка = тот же `assets_sync.py import` против прод-инстанса с прод-env.
Перед этим на проде обязательны `MCP_AUTH_ENABLED=1` + JWT и
`SUPERSET_ASSETS_STRICT=1`. Детали и снипет для CI — `swarm/superset/README.md`.
