```bash

# Isolated contour (cost-only):
cd swarm && make cost-up      # postgres-cost + python-cost + nuxt-cost + nginx-cost
make cost-logs                # tail all cost services
```

## Логи (`app/logship.py`)

Логи раздела — одна JSON-строка на событие в stdout (базовый канал, его собирает
docker) плюс дубль в Logstash/ELK, если задан `LOGSTASH_HOST` (+ `LOGSTASH_PORT`,
дефолт 5044) в `python/cost/.env`. Пусто → трансляция выключена. `service=finance-cost`;
формат общий с Go-API (`finance-api`) и Nitro-роутами Nuxt (`finance-nuxt`), поэтому в
одном индексе ELK всё лежит единообразно.

Отправка асинхронная (поток-демон + очередь) и НИКОГДА не блокирует запрос:
недоступный Logstash не тормозит API, строки отбрасываются, счётчик потерь раз в
минуту уходит в лог. Access-лог каждого запроса пишет middleware в `app/main.py`
(`request_id`, `route`, `status`, `duration_ms`, `user` из `X-Cost-User`); он же
прокидывает `X-Request-Id` — по нему в ELK сшивается цепочка nuxt → go-api → cost.

Новую диагностику пиши через `log(logging.INFO, "сообщение", поле=значение)` из
`app.logship`, а не `print()` — иначе строка останется только в stdout.

### Детали эндпоинтов

#### `GET /filter-options`
- **Новый источник**: OLAP `[DWH].[dim].[groups]` (справочник групп), а не CostHistory.
- Фильтры: `brand_manager` (из `BRAND_FIO`), `level01`–`level05` (из `gr1-gr5`/`group1-group5`), `calc_sign` (статический).
- `level01`–`level05` возвращают `[{id, text}]` для Select2-совместимости.
- `brand_manager` и `calc_sign` — плоские `string[]`.
- `calc_sign` статический: `["ПКПСС", "КПСС", "ПФКСС", "ФКСС"]`.
- Убраны из фильтров: `country`, `family`, `season`, `model`, `articul`.
- Каскад: полный двусторонний между brand_manager и Level01-05.
- Параметры: query params (ключи фильтров, `id` значения для уровней).

#### `POST /load-data`
- Новый эндпоинт для сырых данных с пагинацией.
- Body: `{ date_from, date_to, brand_manager: [...], level01: [...], ..., limit, offset }`
- `limit` макс. 5000, по умолчанию 1000.
- Возвращает: `{ data: [...], count, total, offset, limit }`.

#### `POST /aggregated`
- GROUP BY: `Бренд-менеджер, Модель, Артикул, Признак калькуляции, дата расчета, Уровень цен, Страна пр-ва, Семья, Сезон`.
- AVG-поля: `Розничная цена по уровню, руб.`, `Отпускная цена по уровню, руб`, `Розничная цена по уровню, USD.`, `Отпускная цена по уровню, USD.`, `Пошив, руб.`, `Пошив, USD.`, `Раскрой, руб.`, `Раскрой, USD.`
- SUM-поля: `Основные материалы, руб.`, `Основные материалы, USD.`, `Вспомогательные материалы, руб.`, `Вспомогательные материалы, USD.`, `Декоры, руб.`, `Декоры, USD.`, `Себестоимость, руб.`, `Себестоимость, USD.`
- Фильтры: все 12 полей (level01-05, brand_manager, country, family, season, calc_sign, model, articul).

#### `POST /models-catalog` — окно «Справочник моделей»

Только просмотр: пользователь смотрит, что завела Лиса по модели. Кнопка в шапке
фильтров раздела, окно не связано с выбранной строкой таблицы.

- Body: `{ model?, articul?, naim?, brand_manager?: [], level01?..level05?: [],
  limit?, offset?, all_columns?, all_versions? }`.
- Модель, артикул и наименование ищутся подстрокой; бренд-менеджер и уровни —
  списком значений.
- `all_columns` добавляет к 30 основным колонкам остальные поля представления
  (всего 81); `all_versions` показывает все версии пары модель+артикул вместо
  последней. По умолчанию последняя — на пару бывает несколько записей (модель
  заводят заново, старая остаётся), и соседние строки читались бы как дубли.
- Ответ: `{ data, total, count, limit, offset, columns: [{key, label}] }`. Состав
  и подписи колонок задаёт сервер (`MODELI_COLUMN_LABELS`, `MODELI_MAIN_COLUMNS`
  в `app/db.py`), клиент строит таблицу по ним.

**Бренд-менеджера в `S_MODELI` нет.** Он висит на ПАПКЕ номенклатуры
(`www_folders.BRAND_FIO`, регион `by`), модель ссылается на папку через
`PARENT_ID`, а путь модели совпадает с путём папки во всех 132 047 строках
(проверено 09.09.2026) — оттуда же берутся уровни Level 01-05, сегменты
`FULL_PATH` сходятся с `DWH.dim.groups.group1..group5`. Папок 571, поэтому
фильтры по бренд-менеджеру и уровням сводятся к списку `PARENT_ID` в питоне, без
разбора пути в SQL и без обращения к DWH (это другой сервер).

**Выборка идёт в два шага, и это не преждевременная оптимизация.** `S_MODELI` —
представление из пятнадцати LEFT JOIN, поэтому фильтры, сортировка и пагинация
прямо по нему стоили 5 с на основных колонках и 64 с на всех (замеры
09.09.2026). Поэтому фильтры, отбор версии и OFFSET выполняются по БАЗОВОЙ
таблице `dbo.s_modeli` (есть индексы по ITEM_ID, PARENT_ID, MODEL+ART): 74 мс на
COUNT и 119 мс на ключи страницы, — а данные тянутся из представления по 100
конкретным `ITEM_ID` (~1,1 с). Итого страница со всеми колонками отдаётся за
1,8 с вместо 64.

Подписи колонок расставлены по СОДЕРЖИМОМУ, а не по именам: `SOSTAV` у одежды —
материал крупно, у ЧНИ — размер («29-31»); `NSYRIE` — процентный состав;
`NASSORTIMENT` — код классификатора; `PR1`-`PR4` — прейскуранты. Колонки без
подтверждённого смысла показываются под именем из базы — догадка в подписи хуже
её отсутствия.

#### `POST /details`
- **Изменён**: принимает `model` (строка), не `model + articul`.
- Body: `{ scope?, model?, articul?, construction?, date_from?, date_to?, calc_sign? }`
- `scope` (по умолчанию `model`) выбирает ключ детализации:
  - `model` + `model` — все артикулы одной модели (историческое поведение,
    старое тело `{ model }` работает как раньше);
  - `articul` + `articul` — все модели одного артикула. Режим для ЧНИ
    («Носки&Колготки», Orodoro): там артикул — общая вязка, а модель — её
    цветовой/размерный вариант, и на один артикул приходится до 30 моделей.
    В остальных группах связь 1:1, и режим вернёт одну модель.
  - `construction` + `construction` — все модели и артикулы одной конструкции.
    Конструкция — часть модели до первого дефиса (`107K-1916` → `107K`), то есть
    мужской, женский или детский носок определённого кроя (правило заказчика от
    09.09.2026). Сравнение в SQL идёт по `split_part(TRIM("Модель"), '-', 1)`
    (константа `_CONSTRUCTION_EXPR`); индекса на выражении нет, замер на кэше —
    ~76 мс на 1 млн строк. В «Носки&Колготки» 1341 модель складывается в 306
    конструкций, у крупнейшей (`700K`) 99 моделей и 90 артикулов и 3 789 строк
    детализации за весь кэш. У Orodoro дефиса в модели нет вовсе — конструкцией
    считается модель целиком, и режим совпадает с разбором по модели.
  Сортировка следует за режимом: вторым ключом идут поля, которые в этом режиме
  меняются (у конструкции — `Модель`, затем `Артикул`).
- Делает GROUP BY по `дата расчета, Признак калькуляции, Модель, Артикул, Наименование модели, Номер задания производства`.
- Серверный расчёт: `Себестоимость, руб.` (сумма статей), `Наценка, руб.`, `Наценка, %`, `Маржинальность, %`.
- Новые поля: `Номер задания производства`, `Вязание, руб.`, `Декор, руб.`.

#### `POST /calc-sign-copy` — калькуляция с другим признаком (пункт 1 «Списка доработок»)
- Признак у исходной калькуляции НЕ меняется: создаётся новая калькуляция —
  копия всех строк расчёта с выбранным признаком. Так решил заказчик 27.08.2026.
- Разрешённые признаки: `ПКПСС`, `КПСС`, `ПФКСС` (`CALC_SIGN_COPY_ALLOWED` в
  `app/db.py`). ФКСС не участвует — это история факта, в DWH не пишется.
- Право `cost:calc_sign_copy` — только роли «Калькулятор» и «Full Admin»
  (миграция 0043). Бренд-менеджеру и ПЭО кнопка не показывается.
- Копия создаётся до расценки: если по исходной калькуляции уже есть цена в
  `cost_price_pending` или согласование ПЭО, эндпоинт отвечает 400.
- Номер задания у копии пустой — согласование ПЭО по ней идёт как по одной
  калькуляции. Если у источника задание есть, копируются строки только его.
- Ответ содержит `clash_with_source`: признак уже есть у калькуляции источника.
  Тогда у копии и у неё будет ОДНА цена — цена в разделе ставится на модель,
  артикул, план и признак. Создание при этом не блокируется (решение заказчика:
  пересчёт может понадобиться и после того, как источник свою калькуляцию
  прислал).
- Правки материалов у копии идут обычным механизмом версий; применение версии
  выбирает таблицу по ключу (`_calc_table` в `app/db.py`), иначе DELETE+INSERT
  ушли бы в кэш источника.

#### `POST /save-changes` и `/save-batch`
- Пишут в OLAP `[FinSandBox].[dbo].[CostHistory_Changes]` и дублируют в локальный `cost_price_changes_audit` (postgres-cost).
- В mock-режиме — только локальный аудит.

#### Прейскурант в Лисе — `POST /pending-changes/apply` → `create_priceList_inFox`

Установка цен, кроме записи в DWH, отправляет пакет процедуре Лисы
(`PROC_DB_*` в `.env`, вызов — `call_calc_sign_procedure` в `app/db.py`, текст
процедуры для справки — `sql/create_priceList_inFox_kolomeytsev.sql`).

**Что процедура делает с каждым полем** — знать обязательно, иначе правки идут
наугад:

| Поле JSON | Куда попадает | Условие |
|---|---|---|
| `price_type` документа | `prices.CENA_TIP` — тип прейскуранта | — |
| `wholesale_rub` строки | `prices1.CENA` — цена в прейскуранте | — |
| `plan_price` строки | `s_modeli.PLAN_PRICE` | **только `price_type = 3`** и новое значение больше старого |
| `price_level_id` строки | `s_modeli.PRICE_LEVEL_ID` | **только `price_type = 1`**, значение > 0 и текущий пуст |
| `author_name` документа | `prices.USERVRKV` И `prices.PRIM` («PLAN_ID: … AUTHOR: …») | — |
| `calc_sign` документа | нигде не используется, только протаскивается | — |

`@JSON_IN` — МАССИВ документов, процедура идёт по нему курсором и на каждый
документ создаёт отдельный прейскурант (свой `NOMER` и `PRICE_ID` из
`punictabl`). Поэтому «вызвать процедуру дважды» = положить два документа в один
вызов; отдельные `EXEC` не нужны и хуже — при двух вызовах возможно состояние
«первый прошёл, второй упал».

**Длина автора — 15 символов.** `prices.USERVRKV` объявлен `char(15)`
(`PRIM` шире, `char(100)`, но процедура кладёт в оба поля одно значение, так что
предел задаёт узкое). Проверено по `INFORMATION_SCHEMA` 08.09.2026. Обрезка —
`_fit_author` в `routes.py`, там же константа `_USERVRKV_MAX`.

**Автор — бренд-менеджер строки** (просьба пользователей 08.09.2026). Берётся из
поля «Бренд-менеджер» строки `cost_price_pending`; пусто или «-» — фолбэк на
того, кто нажал кнопку. До этого уходил email нажавшего, обрезанный до 15
символов (31.07 в Лисе записалось `mariy.zuravskay`), а со страницы
`/cost/approvals` — вообще `system`. Все одиннадцать менеджеров укладываются в
15 символов, максимум ровно 15 («МАСЛЕННИКОВА А.», «ТАТАРИЦКИЙ В.П.»).

**Группировка документов** — по (признак, план, бренд-менеджер, вид документа):

- КПСС — отдельный прейскурант на план, ПФКСС — план в ключ не входит;
- **бренд-менеджер в ключе**, потому что он же уходит автором: ПЭО отправляет
  пачкой ассортимент разных менеджеров, и раньше автором всей пачки становился
  один из них (брали первую строку);
- вид документа — `''` обычная строка, `'purchase'` и `'cost'` у закупной.

**Закупная продукция — ДВА документа на одну пачку** (решение заказчика
08.09.2026), у обоих `price_type = 1`:

| Документ | `wholesale_rub` | `price_level_id` | `plan_price` |
|---|---|---|---|
| себестоимость (автор `с/с ФАМИЛИЯ`) | `total_byn` из `cost_purchase_cost` | не передаём (0) | 0 |
| отпускные цены (автор `ФАМИЛИЯ`) | цена бренд-менеджера | как обычно | 0 |

Почему так: тип 3 полез бы обновлять `s_modeli.PLAN_PRICE`, а карточку модели у
закупной трогать не нужно. `price_level_id` только во втором документе — иначе
уровень записался бы из любой строки с типом 1; ноль отсекается условием
процедуры. `plan_price = 0` у закупной в обоих документах: себестоимость едет
отдельным прейскурантом, а сбор отчёта `PLAN_PRICE_DETAILS` внутри процедуры
сделан БЕЗ проверки типа цены, и ненулевое значение засоряло бы ответ моделями,
у которых ничего не обновилось.

Признак закупной — не признак калькуляции (у неё обычные КПСС/ПФКСС), а наличие
раскладки в `cost_purchase_cost`; спрашивается пакетно `purchase.flags_for` по
ключу С ЗАДАНИЕМ. Закупная не смешивается с обычной в одном документе даже при
совпадении признака, плана и менеджера: тип цены задаётся на документ.

Порядок документов в массиве: сначала себестоимость, потом цены.

**Результат вызова виден в логах.** `_run_proc_safe` пишет через `log()`, а не
`print()` (иначе строки остаются только в stdout контейнера и в ELK не
попадают): сколько документов ушло, сколько из них себестоимости, какие авторы,
и что процедура вернула в `@JSON_OUT` — там есть `PLAN_PRICE_UPDATED` и
`PRICE_LEVEL_UPDATED`, по ним сразу видно, что применилось.

#### Мультипаки — `app/multipack.py`, `/multipack/*` (миграция 0049)

Пак (3/5/7 пар в одной единице продажи) — модель-артикул, себестоимость которого
складывается из калькуляций-одиночек плюс материалы упаковки. Слот такой
калькуляции в источнике ЕСТЬ, но пустой: 430A-3839 / B3-263430A «НОСКИ ДЕТСКИЕ
(3 пары)» несёт две строки типа «шт» с нулевой суммой. Заказчик подтвердил
02.09.2026, что паков без слота не бывает (цена пишется обратно в источник по
ключу через процедуру), поэтому калькуляция создаётся не с нуля — наполняется
существующий ключ.

**Строки живут в версии калькуляции, не здесь.** `/multipack/build` только
ГЕНЕРИРУЕТ строки и возвращает их в редактор; сохраняет их обычный
`create-version` / `save-calculation-draft`. Отсюда бесплатно приходят цена,
согласование ПЭО, запись в DWH, блокировки и переживание refresh кэша
(`_reapply_active_versions_to_cache`). Если бы сборка писала в кэш сама, она
обходила бы согласование.

**Свёртка по статьям, а не копирование строк.** Одиночка носков — 20–145 строк;
на пак из трёх пар это 300+ нечитаемых строк. Поэтому на каждую одиночку
генерируется по строке НА СТАТЬЮ: `Норма` = количество штук, `цена материала` =
себестоимость статьи за штуку. Дальше работает штатный `_recalc_cost_buckets`.
Декоры — исключение: у них нормы и цены нет, стоимость задаётся суммой в
«Декоры, руб./USD.» (`_PLAN_DECOR_TYPES`).

**`cost_factor_rub/usd` у сгенерированных строк — всегда NULL.** Коэффициент
источника (миграция 0031) описывает КОНКРЕТНЫЙ материал; у наших строк
произведение точно равно стоимости. Попутно этим же коммитом закрыт баг
`addVersionRow` в `index.vue`: шаблон новой строки копировался с первой строки
калькуляции ВМЕСТЕ с её коэффициентом, а он у трети калькуляций носков далёк от
единицы (25-й процентиль по строкам — 0,000241) — введённая цена молча
обнулялась.

**Состав ключуется на (модель, артикул)** — решение заказчика: пак проходит
ПКПСС → КПСС → ПФКСС одним составом, меняются только суммы одиночек. Снапшот
сумм лежит не на составе, а в журнале сборок `cost_multipack_build`: суммы у
каждого этапа свои, и снапшот на строке состава затирался бы следующим этапом.

**План одиночки — «любой», а не план пака.** Проверено на данных: у пака
`PLAN_ID = 0`, у его одиночек — 6762 / 6982 / 7275 / 7773. Пустой план в составе
значит «взять самый свежий», пустой признак — «этап пака». Пользователь может
зафиксировать и то, и другое (📌 в интерфейсе). Внутри плана берётся задание с
максимальной рублёвой себестоимостью — то же правило, что при простановке цены
(`get_max_calc_cost`).

**Строка состава помечена `свойство3` = `мультипак`.** По маркеру пересборка
отличает свои строки от упаковки (упаковка переносится как есть), а редактор
блокирует ручной ввод: правится состав, а не строка.

**Автопересбора нет.** Изменилась себестоимость одиночки — интерфейс показывает
«было X → стало Y» (`stale` в `GET /multipack`), пересобирает человек. Молча
менять согласованные цифры нельзя.

**Паки исключены из дашборда коммерческой эффективности** (`BASE_CONDITIONS` в
`app/commercial.py`) — их себестоимость собрана из одиночек, которые в базе уже
посчитаны. Условие идёт по составу, а не по колонке витрины: состав правят чаще,
чем идёт `REFRESH cost_calc_mv`. В выпуске (`app/margin.py`) паков нет и так —
производят одиночки, пак только комплектуют.

Право — `cost:multipack` (миграция 0049 выдаёт ролям «Калькулятор», «ПЭО» и
«Full Admin»; у `cost:calc_sign_copy` ПЭО исключён намеренно — это разные
решения заказчика).

#### Семафор этапов (пожелание № 2) — колонка «Этап» главной таблицы

Один значок на строку показывает, где калькуляция в процессе; считает его
`rowStage()` в `index.vue`, и порядок проверок там — от конца процесса к
началу, потому что признаки накладываются (у записанной в DWH строки остаётся и
статус ПЭО, и заявка на цену):

| Значок | Этап | Признак в строке `/aggregated` |
|---|---|---|
| 🟣 | загружено в DWH («лису») | `_in_dwh && !_reopened` |
| 🔴 | отклонено руководителем ПЭО | `peo_status == 'rejected'` |
| 🟡 | цена БМ отправлена на корректировку | `peo_status == 'returned'` |
| 🔵 | цена установлена бренд-менеджером | `_has_pending` (заявка в `cost_price_pending`) |
| 🟢 | себестоимость утверждена экономистом | `peo_status == 'approved'` |
| ⚪ | ещё не согласована | ничего из перечисленного |

Переоткрытая админом калькуляция (`_reopened`) показывает не «в DWH», а текущий
шаг второго круга. Клик по значку открывает окно ПЭО, как раньше. Фильтр
«Статус согласования» остался серверным (`peo_filter` в `get_aggregated`,
`routes.py`) и этапы 🔵/🟣 пока не различает — при необходимости расширять там.

#### Отметка «нужна замена артикула» и рассылка (пожелание № 4)

Колонка «Замена арт.» — галочка в строке (право `cost:articul_replace`, миграция
0052 выдаёт «Бренд-менеджеру», «ПЭО», «Калькулятору» и «Full Admin»). Решение о
замене артикула принимает бренд-менеджер — это уточнение заказчика 03.09.2026,
поэтому БМ здесь основной носитель права, а не получатель следствий. Ключ отметки — как у статуса
ПЭО: модель, артикул, признак, план, задание (`cost_articul_replace`,
`uq_articul_replace_key`, пустые части хранятся как `''`). Наложение на строки
`/aggregated` — `articul_replace.apply_flags`, поля `replace_*`.

При установке галочки `app/articul_replace.py` шлёт сообщение адресатам сегмента:
ЧНИ (`trim("Level 01") IN ('Носки&Колготки','Orodoro')`) → Кочеткова Т., Король Н.;
всё остальное, включая пустой Level 01, → Дащинская А.А. Адресаты — в таблице
`cost_articul_replace_recipients`, а не в коде. Каждая попытка пишется в
`cost_articul_replace_mail` (имя историческое, `channel` = `bitrix`); итог
последней — в `notified_at`/`notify_error` отметки, интерфейс показывает ✉ или
⚠ с причиной. Снятие галочки ничего не шлёт.

**Снять стоящую отметку может только администратор (`cost:admin`).** Заказчик
09.09.2026: калькулятор, ПЭО и бренд-менеджер снимали галочку после отправки —
а отметка уже ушла операторам сообщением, отзывать её молча нельзя. Проверка на
сервере в `articul_replace_set` (403 «может только администратор»), на фронте
чекбокс у стоящей отметки отключён (`canToggleReplace`). Повторная установка
поверх стоящей (needed=true → true) разрешена всем с правом — так повторяют
рассылку, если она не дошла; в интерфейсе это клик по ⚠ (`resendReplace`),
комментарий сохраняется.

**Единственный канал — сообщение в Битрикс напрямую через портал.** У адресата
в `cost_articul_replace_recipients.b24_id` стоит его ID в корпоративном
Битриксе; `send_bitrix` шлёт сообщение через site_api тем же контрактом,
которым Go дублирует уведомления кабинета в Б24
(`POST {id, message: "Finance: …"}` + Basic Auth, ответ `{"success": bool}`).
Переменные `SITE_API_NOTIFY_URL/USER/PASSWORD` — те же имена, что в корневом
`.env`, но читаются из `python/cost/.env`; на проде это CI-переменная
`ENV_FILE_COST` (`swarm/ci-finance.yml`), отдельная от `ENV_FILE` Go-API — 07.09
из-за этого канал на проде был пуст. Без них отметка ставится, а сообщение
помечается `skipped` — это видно и в подсказке к заголовку колонки, и в баннере
после установки галочки. Сбой доставки отметку не откатывает: повтор — снять и
поставить галочку снова. Адресаты без `b24_id` перечисляются в `notify_error`
(«без ID в Битриксе: …»), чтобы экономист не думал, что оповестил всех.

**Почему не через кабинет:** канал Go-API `/internal/notifications` адресует по
`user_id` кабинета, а эти адресаты в Finance Cabinet не заходят (заказчик,
03.09.2026) — номера у них не появится. Первый вариант с `user_id` отброшен по
этой причине. **Почему без почты:** первая версия слала ещё и письмо по SMTP
(`COST_SMTP_*`); 08.09.2026 заказчик решил почтовый канал убрать — почтовой
инфраструктуры у проекта нет, а Битрикс у адресатов есть. Колонка `email` в
справочнике осталась как идентификатор человека и подпись в интерфейсе;
`COST_MAIL_TZ` и `COST_PUBLIC_URL` по-прежнему задают время и ссылку в тексте
сообщения.

#### Статус «Неактуальная модель/артикул» — `app/obsolete.py`

Просьба заказчика 09.09.2026. Калькулятор или ПЭО отмечают, что изделие больше
не актуально (право `cost:obsolete`, миграция 0056 выдаёт «Калькулятору», «ПЭО»
и «Full Admin»; бренд-менеджеру — нет). **Ключ — модель + артикул**, как у
карточки 713: слова заказчика — «если статус поставлен хоть одному ключу
модель/артикул, то все калькуляции становятся с таким статусом». Таблица
`cost_obsolete` хранит последнее состояние с автором и временем, журнала нет.

В интерфейсе: колонка «Неакт.» (галочка, `toggleObsolete` после ответа сервера
обновляет все строки той же пары в `allAggregated`), строка серая
(`tr.row-obsolete`), в колонке «Этап» ⚫ поверх любого этапа (`rowStage`), в
легенде — «неактуальна». Фильтр «Статус согласования» получил значение
«⚫ Неактуальная модель/артикул» — серверное (`peo_filter='obsolete'` в
`get_aggregated`, статус накладывается до фильтра); в остальных значениях
фильтра неактуальные не отсекаются. Галочка «Не показывать неактуальные» —
клиентская, по умолчанию выключена (неактуальные видны серыми, чтобы статус
замечали), помнится в localStorage и в серверных настройках (`hideObsolete`);
при фильтре статуса «неактуальные» она игнорируется, иначе таблица была бы
пустой.

#### Согласование цен по постановлению 713 (пожелание № 8) — `app/reg713.py`

В Беларуси цены на часть ассортимента регулируются постановлением Совмина
№ 713: новинка и повышение цены требуют согласования с исполкомом. Колонка
«713» главной таблицы показывает состояние карточки (`·` не требуется, 📋
требуется без решения, ✅ согласовано, ❌ не согласовано), клик открывает окно.
Право `cost:reg713` — миграция 0053 выдаёт «Бренд-менеджеру», «ПЭО»,
«Калькулятору» и «Full Admin» (решение заказчика 03.09.2026: карточку ведут все
рабочие роли; без права только «Просмотр»).

**Ключ карточки — модель + артикул** (`uq_reg713_key`), без признака
калькуляции, плана и задания — решение заказчика 03.09.2026: «карточка должна
быть привязана вообще к модели-артикулу». Исполком согласует цену изделия, а не
калькуляцию, одно решение действует на все планы и этапы пары. Это крупнее ключа
цены (4 поля) и статуса ПЭО (5 полей) — не «уточнять» его; фронт после
сохранения обновляет все строки пары. Первый вариант с ключом цены отброшен.

**Поля**: `required`, `kind` (`price_increase` | `novelty`), аналог
(`analog_model/articul/name`), его цены `analog_retail/wholesale` со снимком
источника `analog_price_source` (calc | dwh | gpartner | manual) и времени,
`decision` (`approved` | `rejected` | NULL «не рассмотрено»), `decision_doc`,
`comment`. Каждое сохранение — строка в `cost_reg713_log` (было/стало): решение
исполкома — юридически значимый факт, его переписывание должно быть видно.

**Аналог ищется в Gpartner `S_MODELI`** (132 тыс. записей, 111 тыс. пар
модель+артикул; на пару бывает несколько версий — берём последнюю по
`ITEM_ID`). Архивные (`PR_ARH=1`) не скрываем, помечаем и ставим в конец.

**Цены аналога «по тем же правилам, что в главной таблице»** (требование
заказчика), `analog_prices`: (1) последняя калькуляция аналога в
`cost_data_all` — розница и опт «по уровню»; (2) поверх — утверждённая цена в
DWH по ключу этой калькуляции (`fetch_olap_changes`, при недоступности OLAP —
`cost_price_changes_audit`), как накладывается в `/aggregated`; (3) если
калькуляций нет — плановая из `S_MODELI`: `PRICE_MOPT` как опт, розница из
`PRICE_ROZN`, иначе по уровню цен (`PRICE_TYPE1` → `PRICE_TYPE3`, при нескольких
кандидатах ближайший к опт × 1,4 × (1 + НДС) — без различения «Девочкам /

  долларах). **Пошлина — сумма на каждый код ТН ВЭД**, строки появляются сами
  по кодам из строк прихода;

  количество прихода, цена в валюте. Добавляются поиском среди загруженных

  массовым добавлением («выбранные» / «все найденные»; уже добавленные в
  результатах не показываются), «все из выборки» или пустой строкой.
  **Код ТН ВЭД подтягивается сам** из `S_MODELI.KTNVED` по модели и артикулу

  распределено», предупреждает о кодах без пошлины и об отсутствии курса

  строк, строка без количества) останавливают расчёт;
- «Применить» пересчитывает на сервере и создаёт по строке калькуляцию ПФКСС в
  `cost_manual_calc` (`source_calc_sign = 'ПРИХОД'`): основа — строка КПСС той
  же калькуляции, если есть; дата расчёта = дата прихода; в «Основные
  материалы» — итог в бел. рублях; раскладка — в `cost_purchase_cost`

  `rate_date`).
  Окно 🛒 у такой строки показывает план КПСС рядом и отклонение по статьям.
  Применённый инвойс не правится и не удаляется — только новый приход.

#### Скорость `/aggregated`: три правки 04.09.2026

Жалоба «долго грузится закупная продукция, если ставлю фильтр только на неё».
Замер: период 20.08–04.09 отдавал 13 723 строки и 35,9 МБ за 6–9 с, из них
закупных 123. Разложение по этапам (расследование 04.09.2026): плановые цены
Gpartner 2,7 с, агрегат 815 мс, утверждённые цены FinSandBox 740 мс,
сериализация 410 мс, 22 оверлея в Postgres 384 мс, справочники 317 мс.

1. **`purchased_only` — серверный фильтр** (`routes.py`, разбор фильтров
   агрегата). Галочка «🛒 Только закупная» была клиентской: сервер считал весь
   период. Теперь условие `cd.manual_source_sign IN ('ПОРТАЛ','ПРИХОД')` уходит
   в WHERE — и это не просто «фильтр пораньше»: закупные калькуляции живут
   только в `cost_manual_calc`, поэтому предикат отсекает ветку миллионного
   кэша в UNION ALL вьюхи `cost_data_all` (EXPLAIN: cost 15,8 против 212 598).
   Клиент отправляет флаг и перезагружает выдачу по переключению галочки.
   Замер: 9,26 с / 35,9 МБ → **0,86 с / 377 КБ**; строки и все их значения
   совпали с подвыборкой полной выдачи (123 из 123, расхождений 0).
2. **`fetch_gpartner_planned` — `VALUES` + `JOIN` вместо цепочки `OR`**
   (`db.py`). `[dbo].[S_MODELI]` — представление из пятнадцати LEFT JOIN, и на
   каждое условие `OR` сервер прогонял его целиком. Замер на 695 парах:
   OR-цепочка 3429 мс, `VALUES` + `JOIN` + `ROW_NUMBER` **139 мс** (в 25 раз),
   `#temp` + `JOIN` 253 мс. Временную таблицу отбросил замер: она падала с
   «конфликт параметров сортировки Cyrillic_General_BIN против
   Cyrillic_General_CI_AS» (колонки MODEL и ART — `char(25)` в BIN-сортировке, а
   tempdb создаёт свои в сортировке базы). У `VALUES` этого нет: параметр
   приводится к сортировке колонки. Батчи по 500 пар остались — предел
   параметров ODBC. Попутно ушла неопределённость: версия пары выбирается
   `ROW_NUMBER` по `ITEM_ID DESC`, как в `load_gpartner_plan_prices`, а не «как
   пришло от сервера». На 694 парах значения совпали, кроме двух, где `ru_nds`
   стал 22 вместо 10 (разные версии пары в справочнике).
3. **`fetch_olap_changes` — чтение таблицы целиком** (`db.py`).
   `CostHistory_Changes` — 665 строк, а запрос перечислял 4551 ключ цепочкой
   `OR`, и на каждом новом наборе ключей MSSQL компилировал план заново.
   Теперь при наборе свыше 200 ключей таблица читается одним запросом
   постоянной формы, ключи сопоставляются в питоне; на узких наборах (например
   `reg713.analog_prices` с одним ключом) остаётся перечисление батчами.
   Предохранитель: если уникальных ключей в таблице стало больше 20 000, код
   пишет в лог и возвращается к батчам (проверено принудительно — результат
   идентичен). Замер на 4551 ключе: **10 091 мс → 461 мс** (в 22 раза),
   443 записи, расхождений 0.

Итог по замерам: весь период 6–9 с → **3,0 с**, только закупная → **0,86 с**.

**Найдено попутно, не исправлено:** при недоступности VPN один `/aggregated`
ждёт **124 с** — в нём пять подключений к MSSQL (справочник уровней цен,
плановые цены дважды, курс, утверждённые цены), и каждое висит свой
`LoginTimeout=30`. Короткий таймаут плюс отказ от остальных обращений после
первого отвала превратили бы это в считанные секунды. Там же: пять подключений
по 250 мс дают полсекунды на каждый запрос даже при живой сети — справочники
уровней цен и курса стоит кэшировать в процессе.

#### «Разбор ИИ» — `app/insights.py`, `/insights/*`

Блок с наблюдениями под ЛОГИЧЕСКОЙ СЕКЦИЕЙ графиков (не под каждой карточкой):
секция целиком даёт модели возможность связать графики между собой — «маржа
выросла, а маржинальность просела» по одному графику не увидеть.

**Главный инвариант: арифметику считает код, модель только интерпретирует.**
`compute_facts` детерминированно вытаскивает из серий максимумы, минимумы,
изменение от начала к концу, доли, выбросы и разницу двух серий; в промпт уходят
готовые числа, и модель получает прямой запрет считать самостоятельно. Отсюда
три следствия, которые нельзя терять при доработках:

- числа в наблюдениях не выдумываются, их посчитал Python;
- при недоступной модели блок не пустой — те же факты отдаются как есть
  (`degraded=true`), и UI их показывает;
- числа из текста сверяются с входными (`_verify_numbers`, допуск 1 % или 0,05);
  несошедшиеся помечаются в UI как «расчёт модели», а не как данные.

Промптом запрещены: причинно-следственные утверждения (в срезе нет данных о
причинах), рекомендации, смешивание плановых признаков калькуляции с ФКСС,
сложение процентов. Глоссарий раздела (ПКПСС/КПСС/ПФКСС vs ФКСС, ЧНИ, пп,
гранулярность цены) лежит в `GLOSSARY` — модель без него смешивает план с фактом.

**Незакрытый период и охват графиков** (правки 02.09.2026 по замечанию
заказчика — разбор сравнивал несопоставимое):

- `chart_facts` сам помечает последнюю точку серии, если она меньше 20 % от
  медианы остальных: «период почти наверняка НЕ ЗАКРЫТ». Определяется по данным
  серии, без знания календаря. Иначе сентябрь с двумя рабочими днями (маржа
  1 198 BYN против 20 млн) читался моделью как обвал, и она писала «падение на
  99,99 %» — сравнение двух дней с месяцем. Промпт требует сказать о неполноте
  первым наблюдением и считать по закрытым периодам.
- Относительные серии (`%`, `пп`, «темп» в подписи — `_is_relative`) не получают
  ни суммы, ни доли в сумме: сложение процентов бессмысленно, а модель
  послушно повторяла посчитанное — в выдаче было «доля июня в сумме
  маржинальности 13,47 %». Вместо суммы даётся медиана.
- В контексте от фронта есть пункт «Что показано на графиках»: графики динамики
  игнорируют фильтр месяца и всегда рисуют все месяцы года (так устроен
  дашборд). Раньше туда уходило «Период: сентябрь 2026» при девяти месяцах в
  серии, и модель считала, что видит выбранный месяц. Промпт требует
  формулировать «за месяцы, показанные на графике», а не «за выбранный период».

Право — `cost:insights` (миграция 0045 выдаёт ролям «ПЭО» и «Full Admin»).
Настройка — `COST_LLM_*` в `.env`; не задано → `/insights/status` отдаёт
`enabled=false`, и фронт блок не рисует вообще.

**Модель берите БЕЗ режима размышлений.** Замер 01.09.2026, блок «Маржа
выпуска» (2 графика, 13 фактов): `deepseek-v4-flash` — 7 с и 0,00045 $
стабильно; `glm-5` — 28–50 с, 0,0078 $ и половина вызовов падает, потому что
«думающая» модель тратит весь лимит токенов на рассуждения и до JSON не доходит
(`finish_reason=length`). Поддержан только протокол `/chat/completions`: у
opencode zen Claude живёт на `/v1/messages`, GPT на `/v1/responses`, и обе
группы через chat/completions отвечают HTTP 500.

**`reasoning_effort=none` — источник стабильности, не микрооптимизация**
(`COST_LLM_REASONING`, дефолт `none`). Оказалось, что `deepseek-v4-flash` тоже
«думающая», просто её рассуждения не мешают формату. Замер 02.09.2026 на
промпте агентского размера (~6,4 тыс. токенов):

| | время | генерация | сбои |
|---|---|---|---|
| без параметра | 17–127 с | 1448–9571 токенов | 1 таймаут из 5 |
| `reasoning_effort=none` | 2–3 с | 24–28 токенов | нет |

`max_tokens` размышления НЕ ограничивает: при `max_tokens=300` приходил
`completion` под 9,6 тыс. Отсюда и «модель недоступна: ReadTimeout» — модель
думала дольше таймаута. **Канал ни при чём:** DNS 2 мс, TCP 1 мс, TLS 395 мс,
прокси в контейнере не задан, то есть ни сеть, ни VPN не участвуют. Качество от
отключения не страдает — сравнение на одном блоке дало по 5 наблюдений, оба
режима нашли незакрытый сентябрь первым пунктом; с размышлениями модель вдобавок
нарушила запрет считать сама («44,71 пп», которых нет в фактах). Необязательные
поля (`reasoning_effort`, `response_format`) при отказе провайдера выбрасываются
по одному в `post_chat` и запрос повторяется — сборка работает и там, где поле не
знают.

Кэш и аудит — одна таблица `cost_insight_runs` (0045). Ключ кэша `request_hash`
включает модель и все данные графиков, поэтому TTL не нужен: изменилась цифра —
изменился хеш. Ответы из кэша строк в журнал не добавляют.

#### Подключение к модели — `app/llm_settings.py`, `/cost/admin/llm`

Провайдер, ключ, модель, уровень размышлений, таймаут и бюджет исследования
настраиваются из админки (право `cost:llm_admin`) и живут в
`cost_llm_settings` (миграция 0051). **Значение из таблицы перекрывает
`COST_LLM_*` из окружения, пустое поле означает «брать из окружения»** —
поэтому dev продолжает работать по `.env`, ничего не настраивая, а прод
настраивается через интерфейс.

Зачем не через `.env`: на проде он приходит из CI-переменной `ENV_FILE_COST` →
`docker config` → `/var/www/cost/.env`, и смена модели стоила бы полного деплоя
стека. Переключаться приходится по ходу дня — 02.09.2026 модель меняли четыре
раза, а у провайдера разом отвалились Claude, GPT и Gemini. Править
CI-переменную из приложения нельзя: понадобился бы токен GitLab API в
контейнере, да и `docker config` в Swarm неизменяемый — значение всё равно
дошло бы только с деплоем.

Настройки читаются через кэш процесса (`TTL_S = 20`): геттеры в `insights`
синхронные и вызываются на каждом шаге агента, асинхронное чтение БД оттуда не
сделать. `refresh()` дёргается на входе в `analyze()` и `investigate()`, так что
правка применяется к следующему разбору без рестарта — проверено сменой модели
на живом сервисе.

**SSRF — главный риск этой страницы.** Поле «адрес провайдера» это URL, по
которому сервер сам сделает запрос: без проверки администратор заставил бы
python-cost стучаться в postgres, go-api, OLAP или метаданные облака.
`validate_api_base` требует https и публичный адрес, причём **резолвит хост и
проверяет каждый IP** — имя может указывать на `10.0.0.5`. Приватные адреса и
http разрешены только флагом `COST_LLM_ALLOW_PRIVATE=1` (dev с локальной
Ollama), плюс есть белый список `COST_LLM_ALLOWED_HOSTS` — **на проде задавать
обязательно**, иначе право `cost:llm_admin` позволяет отправить агрегаты по
марже любому внешнему адресу.

Ключ хранится в БД открытым текстом (попадает в бэкапы) и отдаётся наружу только
маской. Шифровать смысла мало: ключ шифрования пришлось бы держать в том же
`.env`, к которому мы и стараемся не возвращаться, а доступ к БД раздела и без
того равен доступу ко всей себестоимости.

#### Углублённое исследование — `app/insight_agent.py`, `/insights/ask`

Обзорный блок отвечает «что происходит», исследование — «почему». Пользователь
задаёт вопрос по срезу, агент ведёт многошаговый цикл: план → запрос к данным →
чтение → следующий запрос → вывод.

**Модель НЕ генерирует SQL.** Она вызывает инструменты — `metrics`, `breakdown`,
`drill`, `articles`, `fact_vs_norm`, `cost_structure`, `calc_stages`, — а те
являются проекциями `margin.dashboard()` и `app/calc_structure.py`, то есть того
же кода, что рисует страницу. Два следствия:
числа агента гарантированно совпадают с графиком (агент со своей формулой маржи
начал бы противоречить экрану), и произвольного SQL в системе не появляется —
не нужны ни read-only роль, ни валидатор запросов. Схема витрины к генерации SQL
враждебна: у `"Отпускная цена по уровню, руб"` нет точки на конце, в отличие от
всех остальных, и внешний инструмент на этом спотыкается сразу (проверено
01.09.2026).

Ядро отдаёт весь дашборд одним запросом, поэтому несколько инструментов
обслуживаются одним обращением к витрине (`_Cache`): в замере 7 вызовов
инструментов = 4 запроса.

**Причинность здесь РАЗРЕШЕНА** (в обзорном блоке запрещена), но только
подтверждённая инструментом — модель обязана заполнить `evidence`. Промпт
отдельно требует сначала проверить качество данных: провал `unit_raw_byn` против
соседних месяцев (недозаполненное сырьё в источнике), низкая
`fact_coverage_pct` (факт без фактической ставки минуты), малый `calc_count`.
Именно так руками нашли причину аномалии ЧНИ 01.09.2026.

**Три независимых ограничителя, и каждый нужен:**

| Предел | Значение | Что закрывает |
|---|---|---|
| `MAX_STEPS` | 10 | обращения к модели |
| `MAX_TOOL_CALLS` | 20 | обращения к витрине (за шаг модель может попросить 3) |
| бюджет времени | 180 с (`COST_LLM_AGENT_BUDGET`) | случай, когда шагов и вызовов немного, но все медленные |

Пределы поднимались 08.09.2026 вместе со снятием ограничений на объём ответа —
см. «Глубина разбора» ниже.

**Запуск асинхронный, и это не украшение.** `POST /insights/ask` только стартует
фоновую задачу и отдаёт `job_id`; результат забирается `GET
/insights/ask/{job_id}`. Причина: у `location /api/cost/` в
`swarm/config/cost.conf` не задан `proxy_read_timeout`, то есть действует
дефолтный минутный, и синхронное исследование на 84 секунды бэкенд досчитывал, а
клиент получал 504 (02.09.2026) — снаружи это неотличимо от падения приложения.
Подгонять длительность исследования под таймаут прокси значило бы лечить симптом.

**Состояние задачи — в БД, не в памяти процесса.** Реплика у python-cost одна,
но деплой идёт с `order: start-first`: на время обновления работают два
контейнера, и опрос статуса может попасть в новый. Плюс любой рестарт убивает
asyncio-таск. Поэтому задача живёт строкой в `cost_insight_questions`
(`status`, `progress`, `updated_at` — миграция 0047), и любой контейнер отвечает
про неё одинаково. Брошенные задачи (`updated_at` старше `STALE_JOB_MINUTES`)
показываются как ошибка и не занимают слоты — иначе после рестарта пользователь
видел бы вечный спиннер.

Одновременных исследований не больше `MAX_RUNNING_JOBS` (3): без ограничителя
достаточно подержать кнопку, чтобы запустить десятки агентов. Прогресс
обновляется после каждого обращения к данным — в UI видно, чем агент занят
(«шаг 3: проваливается внутрь группы»), а не пустой спиннер.

Замер асинхронной схемы через nginx (02.09.2026): POST вернулся за 0,05 с,
исследование заняло 48,6 с, 7 шагов, 6 запросов к витрине — то есть дольше
минутного лимита прокси, и это перестало быть проблемой.

**Диалог (миграция 0048).** Вопрос без `thread_id` открывает ветку, с
`thread_id` — продолжает её. В контекст следующего раунда уходит СВОДКА прошлых
(вопрос, вывод, имена вызванных инструментов), а не полная переписка с сырыми
выгрузками: те весят десятки килобайт и, главное, устаревают вместе с витриной —
старое число, поданное как свежее, хуже отсутствия контекста. Нужны те же
данные — агент вызовет инструмент заново, это 1–3 секунды. Глубина — последние
`MAX_HISTORY_ROUNDS` (5) завершённых раундов. `thread_id` входит в ключ кэша:
одинаковый уточняющий вопрос («а почему?») в двух ветках означает разное.

Замер диалога 02.09.2026: «какая группа худшая по маржинальности» → «а где
именно внутри неё хуже всего?» → «это связано с фактической ставкой минуты?».
Агент во втором раунде правильно понял «неё» и провалился внутрь «Аксессуаров» до
подгруппы и артикула, в третьем — проверил гипотезу и ответил «да», но оговорил,
что инструмент не разделяет ставку и время, поэтому утверждать точно нельзя.
Время растёт с историей: 16 с → 106 с → 162 с (промпт больше, шагов больше).

Исчерпание любого отключает инструменты и требует вывод по собранному — это не
отказ. На последнем шаге инструменты отключаются всегда, иначе модель уходит в
новый вызов вместо ответа. Отвечать нужно на КАЖДЫЙ запрошенный вызов, даже
отказом: у tool-сообщения есть `tool_call_id`, и реплика с вызовами без парных
ответов делает следующий запрос невалидным. История сжимается
(`MAX_HISTORY_CHARS`) — к седьмому вызову промпт дорастал до 24 тыс. токенов.

##### Глубина разбора — правки 08.09.2026

Заказчик: «ответы очень сухие, на просьбы углубиться отвечает не очень».
Причина оказалась не в модели, а в наших же ограничителях: 02.09, лечя обрезку
JSON, промпт получил «answer до 400 символов, не больше 4 findings по 200» — и
все ответы в журнале легли в 240–536 символов. Убрано; вместо этого один
жёсткий предел на весь JSON (6000 символов) и `max_tokens` 8000 вместо 4000
(развёрнутый разбор занимает ~7,5 тыс. символов и в 4000 токенов упирался).
Замер того же вопроса до/после: 462 → 1018 символов, 4 констатации → 7
наблюдений со сравнениями.

Промпт теперь требует точку сравнения у каждого числа и разделения вклада:
что дала структура выпуска (сместился микс), а что — экономика позиций.
Добавлено правило сверять направление изменения с числами: модель приводила
верные числа и писала «выросли с 14,88 до 14,22».

**Валидатор чисел обзорного блока пришлось учить знаку.** Как только
наблюдениям разрешили сравнение, модель стала писать «разрыв минус 14,2 пп» и
«на 14,2 пп ниже норматива» — а разница серий в фактах посчитана как `-14.2`.
Валидатор видел `+14,2`, в пуле такого не было, и корректное наблюдение
помечалось выдуманным. Теперь `_normalize_signs` понимает знак словом
(«минус»), а отрицательное соответствие принимается при слове направления
рядом (`_DOWNWARD_WORDS`: ниже, отклонение, просадка…). Сверку по модулю без
этого условия делать нельзя: «маржа +14,2 пп» вместо «−14,2 пп» — не опечатка,
а противоположный вывод, и его валидатор обязан ловить.

##### Структура себестоимости и этапы калькуляции — `app/calc_structure.py`

Просьба заказчика 08.09.2026: «нужно, чтобы агент мог копнуть глубже в
структуру себестоимости: материалы, пошив, раскрой, декоры, сравнивать разные
этапы калькуляций». До этого агент доходил до артикула и останавливался —
дальше витрина отдавала только итоговую себестоимость.

`cost_structure(filters, by=None)` — шесть статей источника (материалы
основные и вспомогательные, пошив, раскрой, декоры, вязание) на штуку и долей,
итог + динамика по месяцам + разрез по измерению. Сверено с дашбордом на
августе 2026: выпуск, себестоимость норматив (4,3992), сырьё (1,7693) и
минуты (7,1102) совпадают до знака.

Три вещи, которые обязательно понимать:

1. **«Прочее» — не ошибка, а свойство источника.** Сумма шести статей ВСЕГДА
   меньше себестоимости: медиана покрытия 79%, минимум 20%. Остаток отдаётся
   строкой «прочее» с пометкой, что источник его не раскладывает. Молча
   опускать нельзя — на этой части строятся выводы о причинах, и в разборе
   бюстгальтеров T-shirt именно «прочее» дало весь рост (2,08 → 4,61 BYN/шт,
   доля 23,6% → 40%). Чтобы копать глубже, нужен состав «прочего» — вопрос к
   тем, кто ведёт калькуляции.
2. **Минуты у норматива и факта ОДНИ И ТЕ ЖЕ.** Из 3255 калькуляций августа
   `sewing_fact_minutes` отличается от `sewing_minutes` в нуле строк; сумма
   пошива различается у 1952, сумма раскроя — ни у одной. Источник ведёт
   только фактическую СТАВКУ минуты. Поэтому минуты отдаются одной величиной,
   а разница выражена ставкой (BYN/мин): у Носки&Колготки факт 0,5234 против
   норматива 0,2891 — вот это и есть ответ на «почему подорожало». Два похожих
   поля «минут норматив» и «минут факт» гарантированно породили бы «минуты
   выросли» на ровном месте.
3. **Фактическая себестоимость считается выражением дашборда**
   (`coalesce(_FACT_B, cost_byn)`), а не прямой суммой `cost_fact_byn`: прямая
   давала 4,4330 против 4,5288 на экране, потому что там, где факт негоден
   (`_FACT_OK`) или пуст, дашборд берёт норматив.

`calc_stages(articul, plan_id=None)` — этапы одной позиции: ПКПСС и КПСС
(плановые), ПФКСС (предварительный факт), ФКСС (факт выпуска). База выборки
здесь НЕ `_MARGIN_BASE` — тот отбирает только ФКСС с объёмом, то есть один
этап из четырёх; ограничение `cost_byn < 1000` тоже снято, потому что на
плановых этапах средняя себестоимость 1099 BYN против 6,50 у ФКСС (встречаются
суммы на партию). Такие строки не выбрасываются, а помечаются — иначе этап
исчез бы, и «плана не было» читалось бы как факт.

Главная ценность — поле `статьи_пропали_на_этом_этапе`: статьи, заполненные на
других этапах ЭТОГО ЖЕ артикула, но пустые здесь. У `25-36412П-7П-3`
себестоимость 18,04 (КПСС) → 19,52 (ПФКСС) → 11,23 (ФКСС), и в ФКСС пусты
пошив и раскрой — это дефект калькуляции, а не экономия. Сравнение «пусто на
всех этапах» в поле НЕ попадает: в первой версии модель написала «во всех
калькуляциях отсутствует вязание, что указывает на неполноту разложения» —
вязание у швейного изделия пусто законно.

Глубже статьи — до конкретного материала («какая нить подорожала») — НЕ
сделано, хотя построчная детализация в `cost_data_cache` есть («Наименование»,
«Норма», «цена материала, руб.»). Свести строки к статье не удалось: у
калькуляции 70 TS N / план 9298 сумма «Норма × цена» по 13 строкам
вспомогательных материалов даёт 61,49, с `cost_factor_rub` — 2,2423, а колонка
«Вспомогательные материалы, руб.» той же калькуляции равна 0,590. Смысл
`cost_factor_rub` и размерность «Нормы» надо выяснять у Лисы; инструмент с
неверной арифметикой хуже отсутствующего.

Фильтры от модели проходят белый список `ALLOWED_FILTERS`; в SQL они попадают
параметрами (`= ANY($n)` в `_collect_params`), конкатенации значений нет. Белый
список — не только безопасность: ядро молча игнорирует незнакомые ключи, и
опечатка модели вернула бы данные по всему выпуску под видом ответа про группу.

Журнал и кэш — `cost_insight_questions` (миграция 0046). Колонка `trace` не
отладочная: вывод о причине проверяется только по ней, и она же выводится в UI
блоком «Как получен ответ». Ключ кэша включает `cost_cache_status.refreshed_at` —
агент ходит за данными сам, и без метки обновления вопрос отдавал бы вывод по
прошлой версии витрины.

Замер 01.09.2026 на `deepseek-v4-flash`: вопрос «почему у Девочкам низкая маржа
в июне» — 7 вызовов, 4 запроса к витрине, 36 с, 0,0036 $; агент опроверг
предпосылку вопроса (50,53 % — максимум за год) вместо того, чтобы её
подтверждать.

## Базы данных (`app/db.py`)

### postgres-cost (asyncpg)
- Пул: `COST_DATABASE_URL`, min_size=1, max_size=8
- Инициализируется в `lifespan`, закрывается при shutdown
- Таблица: `cost_price_changes_audit` (аудит изменений)
- `cost_manual_calc` — калькуляции, созданные в приложении копией с другим
  признаком (миграция 0043). Структура совпадает с `cost_data_cache`.
- `cost_data_all` — представление: кэш источника плюс `cost_manual_calc`.
  ЧИТАЮЩИЕ запросы раздела идут в него; загрузка и обновление кэша, применение
  наборов цен по плану — напрямую в `cost_data_cache`.
- `cost_multipack` / `cost_multipack_item` / `cost_multipack_build` — состав
  мультипаков и журнал сборок (миграция 0049, код `app/multipack.py`). Строк
  расчёта здесь нет: они живут в версии калькуляции.

### MSSQL Checks (pyodbc, read-only)
- `get_mssql_conn()` — чтение `[Checks].[CostHistory]` (~13M строк)
- `get_gpartner_conn()` — чтение `[Gpartner].[s_price_level]`

### MSSQL OLAP (pyodbc, write)
- `get_olap_conn()` — запись в `[FinSandBox].[CostHistory_Changes]`

### Драйвер
- `MSSQL_DRIVER` (по умолчанию `{ODBC Driver 18 for SQL Server}`)
- Все pyodbc-коннекты синхронные, FastAPI запускает их в threadpool
- Параметры: `TrustServerCertificate=yes; Encrypt=optional;`

## Известные пробелы

- **Нет тестов.** Ни одного теста в `python/cost/`.
- **Нет линтинга/форматирования.** Ни ruff, ни black, ни mypy.
- **Нет схем Pydantic.** Роуты принимают `dict` вместо моделей — нет валидации на уровне типов.
- **sync DB вызовы в async FastAPI.** pyodbc синхронный, FastAPI запускает в threadpool — но при ошибках соединения нет таймаутов и retry-логики.
- **Ошибки соединения с MSSQL/OLAP.** Если сервер недоступен, endpoint падает с 500 без внятного сообщения.
- **Нет пула для pyodbc.** Каждый запрос открывает новый коннект к MSSQL/OLAP.
- **Жёстко зашитые SQL запросы.** Все в `routes.py`, нет query builder или ORM.
- **Excel export.** Генерирует HTML, не настоящий `.xlsx`.
