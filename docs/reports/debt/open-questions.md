# Вопросы к автору ТЗ — отчёт «Задолженность»

> Статус: 2026-05-23, после реализации M1+M2+M4.
> Каждый вопрос отмечен **блокер уровня MVP** (нельзя выкатить v1 без ответа)
> или **можно отложить** (есть рабочая заглушка/дефолт, MVP уйдёт без ответа).

## A. Жёсткие блокеры — без ответа MVP неполноценный

### A1. План счетов по странам TR / CZ / GB / CN / KG ⛔
- **В чём вопрос:** в `go/internal/reports/debt/chart_of_accounts.go` сейчас заполнены только РФ/РБ/КЗ/УЗ. Для остальных 5 стран таблица пустая → юрлица из этих стран **в отчёте не появятся** (`KindOther` отфильтрует все строки).
- **Что нужно от ТЗ:** для каждой страны таблица `account_root → {ДЗ | КЗ | Выручка}`. Минимально — для активных юрлиц: `MF FASHION TEKSTIL` (TR), `Mark Formelle EU` (CZ), `Hutchison Trading LP` (GB), `MARK FORMELLE TRADE SHANGHAI` (CN), `МФ КЕЙДЖИ` (KG).
- **Можно в MVP без?** Только если в MVP скрыть юрлица этих стран из фильтра. Это компромисс — но реален.

### A2. Подтверждение мапинга КЗ и УЗ ⛔
- **В чём вопрос:** для КЗ (`1210/3310/3510/6010`) и УЗ (`4000/4010/4090/4300/4800/6000/6300/6910/9010/9020`) я заполнил chart по типовому МСФО-плану. Это **гипотезы**, не подтверждённые ТЗ-приложением.
- **Что нужно от ТЗ:** прямое подтверждение / поправки.
- **Можно в MVP без?** Нет для MFKaz/MFUz юрлиц — высокий риск молчаливо неправильных цифр. Минимальная проверка — сверить наш свод с `FinancialReportСounterparties` за один месяц по одной KZ/UZ-компании.

### A3. Определение «Задолженность ВГО» ⛔
- **В чём вопрос:** в название отчёта вшито «ВГО» (внутригрупповая). Это означает:
  - (a) показывать **только** проводки с `Premaster.ICO=1` (между компаниями группы)?
  - (b) или показывать **всю** задолженность, а ВГО — один из срезов/фильтров?
- **Что нужно от ТЗ:** ответ + дефолт фильтра.
- **Можно в MVP без?** Нет — это меняет дефолтный сценарий. Минимум: ответ «yes/no + default ON/OFF».

## B. Можно в MVP без — но лучше получить ответ

### B1. Гранулярность периода ✅ можно MVP
- **В чём вопрос:** UI ожидает произвольный диапазон `[DateFrom; DateTo]` или строго месяц?
- **Текущая реализация:** произвольный диапазон (любые две даты). Закрывает оба сценария.
- **Можно в MVP без?** Да — текущий вариант покрывает обе модели. Если автор скажет «только месяц» — упростим UI после.

### B2. Учитывать ли ручные корректировки `[002 List of adj-ts]` и `[Adj001SamovyvozInternetShop]`? ✅ можно MVP
- **В чём вопрос:** GLMF включает эти корректировки. Мы делаем по чистому Premaster — корректировки **не учитываем**. По нашему анализу (§8a.3 schema-draft) — обе таблицы это P&L-корректировки (`DrAcc='n/a'`, `CrAcc='n/a'`, `PLDescrBK=RevenueDirect/COGS`), баланс ДЗ/КЗ они не трогают.
- **Можно в MVP без?** Да — для балансовых счетов 60/62/76 наш свод корректен и без них. Но **спросить** обязательно — вдруг есть adj-таблицы, не попавшие нам на глаза, которые трогают 60/62.

### B3. PaymentDueDate / OverdueDays — где брать срок оплаты? ✅ можно MVP
- **В чём вопрос:** `DebtRow.PaymentTermDays` и `DocumentRow.PaymentDueDate/OverdueDays` требуют справочника договоров со сроками. `AgreementsBK` (77 строк) оказался workflow согласования — не справочник.
- **Возможные источники:**
  - (a) `[Payments].[report].[FinDebt1].SUM30/60/90/999` — уже посчитанная ageing-матрица по корзинам. Достаточно для UI «просрочка 0-30/30-60/60-90/90+ дней».
  - (b) Справочник договоров в самой 1С — потребует отдельной выгрузки.
  - (c) Заглушка `0` — UI показывает прочерк.
- **Можно в MVP без?** Да — в UI колонки `PaymentDueDate`/`OverdueDays` пометить как «—». Альтернатива: подсоединить ageing из `CubeBadDebt` (мы решили на него не опираться в §8.1, но как **справочный показатель в drill-down** — приемлемо).

### B4. Multi-currency: единая нормализация или каждое юрлицо в своей? ✅ можно MVP
- **В чём вопрос:** `DebtRow.Currency` сейчас = функциональная валюта юрлица (BYN для РБ, RUB для РФ, KZT для КЗ и т.п.). Когда показываем 5 юрлиц вместе — у каждой строки своя валюта.
- **Варианты:**
  - (a) Оставить каждую строку в своей валюте, UI группирует.
  - (b) Опционально показывать всё в одной валюте (BYN/USD) — потребует pull `CurrencyDaily` курсов.
- **Текущая реализация:** (a). Колонка `AmountBYN` не заполняется.
- **Можно в MVP без?** Да — UI работает с разными валютами. Конвертация — M5.

## C. Архитектурные / информационные

### C1. Готовые витрины `FinancialReportСounterparties` и `CubeBadDebt` — почему не используем? ℹ️
- **В чём вопрос:** в FinDWH уже лежат **готовые** агрегаты по контрагенту (`FinancialReportСounterparties`, 288K строк) с готовыми `Opening/Turnover/Closing × Debit/Credit × Currency` помесячно. И готовый ageing-куб `CubeBadDebt` (5.6M). Мы решили считать сами по `Premaster1C`.
- **Зачем спросить:** валидировать решение. Кандидатные причины (§ 8.1 schema-draft): контроль свёртки, гранулярность, расхождения с 1С, зависимость от чужого ETL.
- **Влияние на MVP:** нет — наш свод работает без них. Но без явного «да, идём своим путём» от автора — можем повторить чью-то работу впустую.

### C2. CompaniesMF 18 vs ТЗ 15 — какие 3 юрлица не наши? ℹ️
- **В чём вопрос:** в `[FinDWH].[dbo].[CompaniesMF]` 18 строк, в `seed.go::entities` 15. Расхождение в 3 юрлица.
- **Зачем спросить:** убедиться, что мы не пропустили активную компанию. Возможно 3 «лишние» — это архивные / dummy.
- **Влияние на MVP:** низкое — если в фильтр прилетит неизвестный INN, юзер увидит «нет данных».

### C3. Что считать выручкой: только `Cr 90.01.x` или всё `90.x`? ℹ️
- **В чём вопрос:** в РФ:
  - `90.01.1` — выручка от продаж РФ
  - `90.02` — себестоимость продаж
  - `90.03` — НДС
  - `90.07` — расходы на продажу
  - `90.09` — прибыль/убыток от продаж
- Мы сейчас классифицируем root `90` как `KindRevenue` целиком → все эти подсчёта попадут в `RevenuePeriod`. Это **неправильно для бизнес-смысла «выручка»** — нужно только `90.01.x`.
- **Что нужно от ТЗ:** уточнить — `RevenuePeriod` это вся реализация по `90.01.*` или другая комбинация.
- **Можно в MVP без?** Да, но цифры выручки в текущей реализации **завышены** на остальные субсчета. Чинится переходом chart_of_accounts на уровень субсчёта (нужно немного дописать `chart_of_accounts.go`).

### C4. Subaccount в группировке: 62.01 отдельно от 62.02? ℹ️
- **В чём вопрос:** мы сворачиваем по корню (`62.01`+`62.02` → `62`). UI показывает один счёт `62`. Это нормально для ВГО-задолженности или нужно отдельно «авансы покупателей (62.02)» / «расчёты с покупателями (62.01)»?
- **Можно в MVP без?** Да — текущая свёртка покрывает 95% запросов. Drill-down всё равно покажет конкретные субсчета.

### C5. Доступ — финансист видит только свои юрлица или весь ГК? ℹ️
- **В чём вопрос:** в кабинете есть `useScope` с ролями. По умолчанию `ROLE_FINANCE_ADMIN` видит всё. Нужен ли scope «региональный финансист видит только TR-юрлица» (например)?
- **Текущая реализация:** все, у кого `hasScope('finance')` — видят весь фильтр.
- **Можно в MVP без?** Да — добавить ACL по странам можно позже без рефакторинга UI.

### C6. Excel-export — приоритет MVP? ℹ️
- **В чём вопрос:** в MP `useDebtReport` уже есть готовый паттерн экспорта (видели в cost-разделе). Включать в MVP или v2?
- **Можно в MVP без?** Да, кнопка «Скопировать как TSV» через Ctrl+C закрывает 80% случаев.
