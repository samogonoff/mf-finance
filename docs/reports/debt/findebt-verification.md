# Проверка источника `Payments.report.FinDebt1/2/3` (аналитик, 02.07.2026)

> Аналитик (Maxim Zhurkin) принёс готовый расчёт ВГО-задолженности из вьюх
> `Payments.report.FinDebt1/2/3` + пояснительную записку + эталонный Excel от
> Куликовой (`var/vgo/`). Здесь — результат сверки этого источника с живым OLAP
> (`10.10.6.15`, снэпшот `Date = 2026-05-31`) и что он меняет в нашем отчёте.
>
> Проверял утилитой `go/cmd/vgoprobe` (одноразовая, не для merge).

## 1. Вердикт: источник сходится с 1С копейка-в-копейку

Контрольная пара **ООО «Марк Формэль» → контрагент «Формэль», 31.05.2026**,
`CUR_FILTER = 'В бел. рублях'`, `Channel = 'ГРУППА КОМПАНИЙ'`:

| Показатель | FinDebt1 | Эталон (Куликова / 1С / аналитик) |
|---|---:|---|
| ДЗ (Дебиторская) | **866 791.74** | 866 791.74 ✓ |
| КЗ (Кредиторская) | **−53 196 999.09** | «53 с копейками миллиона» ✓ |

Разбивка КЗ по счетам (колонка `Acc` заполнена во вьюхе):

| Счёт | Сумма BYN | Что это |
|---|---:|---|
| 62.1.1 | +866 791.74 | обычная реализация (ДЗ) |
| 60.1.1 | −1 046 431.05 | расчёты с поставщиком |
| 60.1.3 | −136 703.40 | расчёты с поставщиком |
| 62.4.1 | −52 013 864.64 | **авансы полученные** (не долг за товар) |

`60.1.1 + 60.1.3 = −1 183 134.45` — ровно та цифра, которую Куликова ждала на
счёте 60 (лист «вопросы» в Excel).

## 2. Документная детализация (`FinDebt3`) тоже сходится

Запрос аналитика (`var/vgo/сумма по докам.txt`) — агрегат `FinDebt3` по документам
для той же пары:

| DEBT_FILTER | SUM_D | SUM_K | docs |
|---|---:|---:|---:|
| Дебиторская | 866 791.74 | 0 | 111 |
| Кредиторская | 0 | −53 196 999.09 | 735 |

То есть документный разрез (`FinDebt3`) агрегируется ровно в свод (`FinDebt1`).
«Разбивка ДЗ/КЗ по документам», которую аналитик не мог свести, сходится, если
классификацию ДЗ/КЗ брать из `FinDebt1` (через `DebtClass`-CTE по `Acc`), а суммы —
из `FinDebt3.SUM_D/SUM_K`. Это его финальный рабочий запрос.

## 3. Ключевые свойства вьюх (проверено)

### `FinDebt1` — суточный снэпшот остатка (не журнал)
- Классификация **ДЗ/КЗ уже сделана**: `DEBT_FILTER ∈ {Дебиторская, Кредиторская,
  «Отображать платежи и отгр.»}`. Служебное значение отсекаем явно.
- **Счёт заполнен** (`Acc`: `60.1.1`, `62.4.1`, …) — своя классификация счетов не нужна.
- **Корзины просрочки посчитаны**: `SUM30/SUM60/SUM90/SUM999`.
- **Обороты**: в строках `«Отображать платежи и отгр.»` лежат `D/K_Payment`
  (оплаты) и `D/K_Wholesales` (отгрузка/выручка); в ДЗ/КЗ-строках они = 0.
- Период: `DATE_F/DATE_T/DAYS` (для пары май: `2026-05-01 … 2026-05-31`, 31 день).
- История: `2021-01-31 … 2026-06-30`, 95 снэпшотов. **До мая 2026 — помесячно,
  с 2026-06-01 — посуточно.**

### `CUR_FILTER` — три «линзы» одной суммы (ловушка ×2)
`{В валюте, В бел. рублях, В долларах США}` — это НЕ валюта, а представление той же
суммы. Фильтровать только по `Currency`, не пиннинг `CUR_FILTER` → **сумма
задваивается**. Для BYN-долгов пары `'В валюте'` и `'В бел. рублях'` совпали
(обе −53 196 999.09) — задвоения нет, пока `CUR_FILTER` зафиксирован.
**Решение (рекомендация Maxim): пинним `CUR_FILTER = 'В бел. рублях'`** — движок сам
консолидирует все валюты в BYN, одна строка на долг. `Currency` при этом остаётся
родной (`BYN/RUR./USD`), но `SUM` уже в BYN.

### `FinDebt3` — документная детализация
- `Doc_Number, Doc_Date, Payment_Date, DAY_DELAY, Delay, Doc_Description`, суммы
  `SUM_D/SUM_K` + корзины `SUM{30,60,90,999}_{D,K}`.
- `CUR_FILTER` здесь: `{В валюте договора, В бел. рублях, В долларах США}`
  (обрати внимание — «В валюте **договора**», не «В валюте»).
- `FinDebt1.Channel == FinDebt3.Folder`.
- **Просрочка заполнена**: ВГО-контур 31.05.2026 — 6462 документа, из них 3150 с
  `Payment_Date`, 1786 просрочены (`DAY_DELAY > 0`). Закрывает открытый вопрос №1.

## 4. ВГО-контур

`Channel = 'ГРУППА КОМПАНИЙ'` — единственное значение, несущее ВГО-баланс
(варианты-опечатки `ГРУППА КОМПАНИИ`/`ГРУППА КОМПНИИ МФ`/`Группа компании` на этот
снэпшот пустые). Итог по всей группе 31.05.2026, BYN:

| | ДЗ | КЗ |
|---|---:|---:|
| Всего (9 ЮЛ) | +270 440 040.87 | −271 232 640.13 |

Почти симметрично (разница ~792 тыс. — таиминг/округление), как и должно быть у
внутригрупповых расчётов (ДЗ одной стороны = КЗ другой). Зеркальная сверка пары
подтверждает: Формэль→Марк Формэль = ДЗ 53 169 577.34 / КЗ −1 040 868.57 против
МФ→Формэль = ДЗ 866 791.74 / КЗ −53 196 999.09.

`UNP` контрагентов совпадают с нашим `seed.go` (15 ЮЛ), но есть нюансы:
- у одного УНП несколько написаний имени (`МАРК ФОРМЭЛЬ ТЕКС` / `… ООО` / `Текс ООО`);
- часть строк с `UNP = 'Не определено'` (MARK FORMELLE EU, Shanghai, часть KZ) —
  добить через `[FinDWH].[dbo].[CompaniesMF]` (вопрос №1 из Excel Куликовой).

## 5. Что это меняет — закрывает 5 наших открытых вопросов

`FinDebt` — это ровно тот «источник недоверия», от которого мы сознательно ушли
(`payments-source-map.md` §3, `schema-draft.md` §8a). Но аналитик доказал
копейка-в-копейку, и он закрывает всё, что висело в `analyst-handoff.md`:

| Открытый вопрос | Наша боль | FinDebt |
|---|---|---|
| №1 Срок/просрочка | искали в Docs через GUID-мост | `FinDebt3.Payment_Date/DAY_DELAY` + корзины `SUM30/60/90/999` |
| №2 План счетов 5 стран | не знали, какие счета — долг | ДЗ/КЗ уже в `DEBT_FILTER`, `Acc` заполнен |
| №3 План счетов КЗ/УЗ | ставили по предположению | классификация уже сделана апстримом |
| №4 Выручка: весь 90 или 90.01.x | резали корень 90 сами | `D/K_Wholesales` — отдельные обороты |
| №5 Договор/документ | эвристика субконто, GUID-мост | `FinDebt3` = готовый документный разрез |

Остаётся один компромисс (честно): мы **перестаём контролировать цифры сами** —
их считает чужой ETL (`Debt_arh`→`FinDebt*`). Риски §3 `payments-source-map.md`
(зависимость от их ETL, неизвестная формула просрочки, ограниченный период)
остаются. Копейка-в-копейку с 1С — сильный аргумент, что компромисс оправдан.

## 6. Как перестраивать (предложение)

Аддитивно и обратимо: **новый бэкенд `DEBT_BACKEND=findebt`** рядом с
`mssql/ch/finpl`, реализует тот же `PremasterRepo` (Report + Drilldown),
маппится на существующую `DebtRow` → **правок модели/UI не требует**.

- **Report** — свод из `FinDebt1` на снэпшот `DateTo` (закрытие) и `DateFrom`
  (открытие, `MAX(Date) < DateFrom`); оборот = закрытие − открытие. Группировка
  `(Organisation → Contragent/UNP → Acc → Currency=BYN)`, `Channel='ГРУППА КОМПАНИЙ'`,
  `CUR_FILTER='В бел. рублях'`, `DEBT_FILTER != 'Отображать платежи и отгр.'`.
  ДЗ = `SUM(Дебиторская)`, КЗ = `−SUM(Кредиторская)` (знак → в наш «положительный долг»).
- **Drilldown** — рабочий запрос аналитика по `FinDebt3` (документы с
  `Payment_Date/DAY_DELAY`, суммы `SUM_D/SUM_K`, классификация ДЗ/КЗ из `FinDebt1`).
- **Просрочка** — v1: `DAY_DELAY` на уровне документа в `OverdueDays`. Корзины
  `SUM30/60/90/999` вьюха даёт даром — если нужны в своде, расширяем модель+UI.
- Config + `.env.example` (`MSSQL_PAYMENTS_DB=Payments`, схема `report`, вьюхи) —
  в том же коммите (правило env-переменных).

Открытый выбор масштаба вынесен в вопрос пользователю (аддитивный бэкенд /
+корзины в UI / полная замена старых бэкендов).
