# Runbook: отчёт «Задолженность ВГО» из сырых таблиц (DEBT_BACKEND=arh)

Третий бэкенд отчёта (дефолт — `findebt`, второй — `findebt-docdate`). Суммы, документы,
договоры/сроки и продажи собираются НЕ из готовых вьюх FinDebt1/3, а из сырых таблиц OLAP
(БД Payments, схема dbo): `Debt_arh`, `Docs`, `Wholesales_arh`.

Поток: **MSSQL сырые таблицы → CH `finance.fact_arh_debt` / `fact_arh_sales` → отчёт**.
Заливка встроена в реплику FinDWH: тот же воркер, журнал `finance.findwh_etl_runs`, проверка
«уже загружено сегодня», прогресс и страница `/admin/etl` (строки `arh_debt`, `arh_sales`).

> **Продажи = брутто; «Возвраты» заполняет только `arh`.** В `findebt` `K_Wholesales` на 90 — брутто
> (`D_Wholesales` на 90 всегда 0; МФ 690591512 на 30.09.2026: K = 51 526 516 = Σ положительных строк
> `Wholesales_arh`, возвраты −4 107 871 не учтены), колонки «Возвраты» там пустые («—»).

## Правила пересборки (сверены на живом OLAP)

| Что | Правило |
|---|---|
| Остаток | `Debt_arh.Sum` на дату снэпшота `Date` (23:59:59, берём по дню). Плюс = ДЗ, минус = КЗ (`DtKt` не используется) |
| **Нетто по документу** | В отчёте ДЗ/КЗ считаются как у FinDebt: для НЕПУСТОГО `doc_id` сначала нетто `sum_d + sum_k`. РБ/РФ/УЗ сворачиваются внутри (дата, ЮЛ, контрагент, **счёт**, валюта). Только КЗ сворачивается между счетами внутри (дата, ЮЛ, контрагент, валюта): положительный итог остаётся на счёте с наибольшей ДЗ документа, отрицательный — на счёте с наибольшей по модулю КЗ; при равенстве берётся больший номер счёта. Строки без `doc_id` не сворачиваются. Фильтр счёта применяется после нетто. Один и тот же SQL-вид используется для свода и drill-down |
| Корзины просрочки | `Sum30/60/90/999` = менее 30 / 30–60 / 60–90 / свыше 90 дн.; при нетто — нетто корзин на стороне нетто документа. Если хотя бы одна корзина имеет знак, противоположный итогу документа, **все четыре корзины документа обнуляются**, как в FinDebt3. Σ корзин < остатка, разница = «без просрочки» (`Aging.Current`) |
| Контур ВГО (остатки) | `Chnl` или `Folder` = `ГРУППА КОМПАНИЙ` (у УЗ/КЗ `Chnl` пуст) |
| Документ/договор/срок | `Debt_arh.DocID → Docs.ID`; договор = `Docs.ParentID` (второй join), нет родителя — сам документ. `Docs` читается с дедупом по ID (дубли нулевой записи). `DATE_DOC` не используется |
| Продажи | `Wholesales_arh.Sum` по корню `CrAcc` ∈ {90, 6010, 9010}; страновую привязку (КЗ — 6010, УЗ — 9010) делает отчёт (`revenueAccCondition`). Знак — см. ниже. Плюс = продажа, минус = возврат, показываются раздельно |
| «За последний месяц» | календарный месяц, предшествующий месяцу даты `to` |
| BYN/USD | сумма × `currency_daily.curr_rate` НА ДАТУ СНЭПШОТА (остатки) / СОБЫТИЯ (продажи); BYN (933) — курс 1; USD = BYN / курс USD (840). «В валюте договора» — родная сумма с подписью по ISO-коду |

### Знак продаж по странам

- РБ/РФ (90.x) и УЗ (9010): плюс = продажа, минус = возврат.
- **КЗ (141240004842): продажа Дт 1210 / Кт 6010 в источнике идёт со знаком МИНУС** (сентябрь 2026: 2070 строк,
  −389.6 млн по всем каналам; по ВГО лишь 4 строки, −266 тыс.). Для ЮЛ КЗ знак инвертируется
  (`eff_sign`). Это эмпирика из данных — **подтвердить с аналитиком**.
- **У КЗ выручка по ВГО по 6010 фактически нулевая**: ВГО-отгрузки КЗ идут по Кт 3310 / Дт 1310 и 1330
  (сентябрь ≈ +206 млн) и в правило 6010 не попадают. **Не включать их без решения аналитика.**
- Возвраты УЗ: счёт 9040 в данных ВГО за сентябрь 2026 не встречается (у УЗ Кт: 9010, 9350, 9420, 9620, …) —
  однозначного правила нет, **открытый вопрос**, в правило не добавлено.

## Что и как грузится (лёгкий инкремент, замена даты через stage)

- Окно остатков: последние `ARH_WINDOW_DAYS` (45) дней ежедневно + концы месяцев от
  `DEBTARH_RAW_MIN_DATE`. Продажи: каждый день от `DEBTARH_RAW_MIN_DATE`.
- Каждый запрос к MSSQL — одна дата или чанк ≤ 7 дней (продажи — ≤ 31) по `Date`, с фильтром по
  нашим `UNPOrg` (индекс `Debt_arh (UNPOrg, Date)`). Факты ограничены ВГО-каналом, а проверка
  присутствия ЮЛ и отпечаток читают все его каналы. Даты в параметрах — `YYYYMMDD`.
- На каждое присутствующее в `Debt_arh` ЮЛ и дату ETL добавляет нулевую строку
  `acc=doc_id='__snapshot__'`. Она позволяет отличить реальный нулевой ВГО-баланс от остановки
  загрузки ЮЛ; суммы, курсы и строки отчёта этот маркер не затрагивает.
- **Отпечаток дня** = `MAX(DateChange)` + число строк источника за весь контур наших ЮЛ; хранится в
  `finance.fact_arh_day_fp` и пишется ТОЛЬКО после успешной замены даты.
- **Замена даты** (1С перезаписывает прошлые даты): дата грузится в уникальную для запуска `fact_arh_*_stage_<pid>_<time>_<seq>` (основная
  таблица не тронута) → число строк сверяется → маркер «не загружена» в `fact_arh_day_fp`
  (`src_rows = 0`) → `ALTER TABLE … DELETE` по дате (`mutations_sync=1`, клиент с таймаутом 10 мин) +
  `INSERT … SELECT` из stage (секунды) → отпечаток дня. Обрыв на любом шаге: до замены основная
  таблица и прежний отпечаток целы, stage удаляется; после DELETE — отпечаток остаётся маркером; в обоих
  случаях дата перепланируется на следующем прогоне. Окно между DELETE и INSERT — секунды.
- Stage-таблицы, оставшиеся после SIGKILL/OOM/рестарта, удаляются в начале следующего прогона, если они старше 12 часов.
- Дата, исчезнувшая в источнике, но оставшаяся в CH (по отпечатку или по строкам данных), удаляется.
- Один прогон в сутки после `ARH_READY_AFTER_HOUR` (по часам MSSQL); повтор в тот же день не грузит.
- Чтение — с `NOLOCK`: в Payments `READ_COMMITTED_SNAPSHOT` выключен (в FinDWH включён), осознанный
  риск «грязного» чтения тот же, что в других extract'ах по Payments.

## Замеры (OLAP, 30.09.2026, read-only)

| Запрос | Строк | Время |
|---|---|---|
| Остатки ВГО одного дня (Debt_arh + Docs ×2) | 20 354 | ≈ 49 с |
| Отпечатки остатков, чанк 7 дней | 8 дат | ≈ 15 с (окно 45 дней ≈ 1.5 мин) |
| Продажи ВГО одного дня | 416 | ≈ 2 с |
| Отпечатки продаж, чанк 31 день | — | ≈ 2 с |

Типичный дневной прогон = отпечатки окна (~1.5 мин) + 1–3 перезагруженные даты (~1 мин каждая).
Полная локальная пересборка 23 дат 22.10.2026 заняла 248 с для остатков и 20 с для продаж.
Запросы отчёта прогнаны на локальном ClickHouse 24.3 по всем трём линзам для РБ, РФ, ПТИР, КЗ и УЗ;
дополнительно свод и drill-down проверены на ClickHouse Playground 26.11 с синтетическими
межсчётными документами. Остальное покрыто Go-тестами с httptest/fake.

## Env (go-api / `cmd/findebt-etl`)

```
DEBT_BACKEND=arh
ARH_SYNC=1                      # включить потоки в воркер реплики
FINDWH_SYNC_INTERVAL=3600       # воркер реплики (общий с GLMF/Table_Fin_PL/ExRates), >0
MSSQL_DEBT_ARH_FQN=[Payments].[dbo].[Debt_arh]
MSSQL_WHOLESALES_ARH_FQN=[Payments].[dbo].[Wholesales_arh]
MSSQL_DOCS_FQN=[Payments].[dbo].[Docs]
DEBTARH_RAW_MIN_DATE=2026-06-01
ARH_WINDOW_DAYS=45
ARH_READY_AFTER_HOUR=13
CURRENCY_SYNC_INTERVAL=21600    # курсы currency_daily (или вручную MODE=currency)
```

При старте go-api пишет предупреждения: `DEBT_BACKEND=arh` при `ARH_SYNC=0` и `ARH_SYNC=1` при
`FINDWH_SYNC_INTERVAL=0` (в обоих случаях `fact_arh_*` не наполняются воркером — отчёт будет пустым).

Курсы: `finance.findwh_ex_rates` НЕ подходит (только USD, `valuta_id` не ISO-код), поэтому
используется `finance.currency_daily` (миграция 010, `[SRV-SQL].Checks.dbo.CurrencyDaily`:
KOD 156/398/643/840/860/978, BYN-строк нет — курс 1 зашит в отчёт).

### Нет курса (фактическое поведение)

Для линз BYN/USD ASOF-подключение без курса даёт 0, а не NULL. Поэтому: строка **не пропадает** (фильтр
пустых строк смотрит на родные суммы), но её пересчитанные суммы равны 0 (родную сумму НЕ подставляем —
это смешало бы валюты). На каждый запрос отчёта в лог go-api пишется одно сообщение со списком
«валюта@дата» без курса (`debt.arh: нет курса для линзы …`), а при пустой `currency_daily` — отдельное
`finance.currency_daily ПУСТА …`. Линза «В валюте договора» от курсов не зависит.

## Даты отчёта и окно снэпшотов

Ежедневные снэпшоты остатков хранятся только за последние `ARH_WINDOW_DAYS` дней (и обновляются при
изменении в источнике); раньше окна доступны **только концы месяцев**, старые дневные даты
**заморожены** (не обновляются и не удаляются). Если ближайший снэпшот ≤ `date_to` дальше 3 дней от
`date_to` (или ближайший < `date_from` дальше 3 дней от `date_from`), отчёт отвечает **HTTP 422**:
«нет снэпшота на дату …; ближайший: …» вместо молчаливой подмены датой конца месяца. Если снэпшота до
`date_from` нет вовсе — период начинается с первого загруженного снэпшота (остаток на начало = 0).
Снэпшоты ищутся с учётом выбранных ЮЛ. Свежесть проверяется отдельно по каждому выбранному ЮЛ,
которое уже встречалось в `fact_arh_debt`: свежий снэпшот одной компании не скрывает остановку
загрузки другой. Для каждого ЮЛ свод использует его собственные ближайшие даты закрытия и открытия,
поэтому допустимый лаг из-за выходного или локального праздника не превращает остаток в ноль. Если
лаг больше трёх дней, HTTP 422 перечисляет отставшие ЮЛ и даты их последних снэпшотов. Нулевой
`__snapshot__` поддерживает свежую дату ЮЛ, когда его ВГО-баланс полностью погашен; расчётные запросы
отбрасывают маркер до свёртки сумм и проверки курсов.

## Договоры и drill-down

Группа «(без договора)» (пустой ключ договора) получает в `contract_ref` маркер `__none__`; фронт
передаёт `contract_ref` в drill-down как есть, и сервер фильтрует `ключ договора = ''` (раньше пустая
ссылка показывала все документы счёта). Пустая ссылка (старые URL) — по-прежнему без фильтра по договору.
Пустой `partner_inn` (контрагент без УНП) разрешён: фильтр `counterparty_id = ''`.

## UI: глубина долга

Если по стороне (ДЗ/КЗ) остаток ≠ 0, а все корзины просрочки = 0, пять колонок глубины этой стороны
показываются как «—» (снэпшоты `findebt` до миграции 014 и повторного `MODE=bootstrap` так и выглядят;
для `arh` это ещё и честный «нет данных о просрочке»). Сервер ничего не скрывает: `Aging.Current` = остаток −
Σ корзин, решение — на фронте. Побочный эффект: строка, где весь долг без просрочки, тоже покажет «—».

## Как залить

1. Миграция CH `015_arh_raw` накатывается CI (`swarm/migrate-clickhouse.sh`), идемпотентна.
2. Курсы: `MODE=currency /findebt-etl` (если не включён воркер курсов).
3. Заливка вручную (минуя «сегодня уже загружено» и час готовности):
   ```sh
   docker exec -e MODE=arh "$TASK" sh -c 'set -a; . /etc/api.env; set +a; exec /findebt-etl'
   # перезагрузить все даты окна, игнорируя отпечатки:
   docker exec -e MODE=arh -e ARH_FULL=1 "$TASK" sh -c 'set -a; . /etc/api.env; set +a; exec /findebt-etl'
   ```
4. Дальше — воркер (`ARH_SYNC=1`), статус на `/admin/etl`.

## Известные ограничения и открытые вопросы

- **Валюта РФ = 643 везде** (в `Debt_arh` у ЮЛ РФ сумма всегда рублёвая) — известное ограничение источника.
- **НДС в `Sum` неизвестен** (включён или нет) — как в источнике, не пересчитывается.
- **Название ЮЛ** в сырых таблицах отсутствует — берётся из seed отчёта по УНП (колонка `company` в CH пуста).
- Даты `Docs` вне 1970–2100 (`0001-01-01`, `2202-…`) считаются пустыми; `Docs.DocType = 'NULL'` — пусто.
- Продажи КЗ и возвраты УЗ — см. раздел «Знак продаж по странам».

## План: два сырых потока (findebt-docdate и arh)

`findebt-docdate` (миграция 011, `debt_facts`/`turnover_facts`, пересчёт на дату документа) и `arh` читают
одни и те же сырые таблицы, но `arh` полнее: документ/договор/срок из `Docs`, нетто по документу, корзины,
возвраты, отпечатки по `DateChange` и интеграция в реплику с `/admin/etl`. **Рекомендация: оставить `arh`,
`findebt-docdate` вывести** (убрать бэкенд, `repo_findebt_docdate_ch.go`, `extract_debtarh.go`, воркер,
миграцию 011 оставить как есть/пометить устаревшей) после приёмки `arh` аналитиком; до тех пор оба живут
параллельно, ничего не удалено. Курсовой `currency_daily` останется общим.

## Откат

`DEBT_BACKEND=findebt` (дефолт). Таблицы `fact_arh_*` не мешают; миграция 015 откатывается down-файлом
(`DROP TABLE IF EXISTS` старые общие stage/fp/факты; динамические stage-таблицы ETL удаляет сам).
