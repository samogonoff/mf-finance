## 1. Диагноз: почему сейчас непонятно

Прошёл по модулю глазами трёх ролей. Проблемы не в отдельных экранах — в архитектуре навигации.

**1. Четыре точки входа с пересекающейся семантикой.** `/plans` (список PL) → `/plans/[id]`
(карточка с таймлайном) → `/plans/process/[id]` (кокпит заданий) → `/plans/tasks` (мои задания).
Три из них показывают одни и те же задания в трёх разных вёрстках. Плюс legacy `/plans/mp.vue`
(read-only факт) — вообще осиротевший экран. Пользователь, зашедший впервые, не понимает,
где «его» место.

**2. Нет ответа на вопрос «что мне делать сейчас».** Дашборд `/plans` показывает
«Экземпляров PL: 3 · Заполнено ячеек: 412 · Активный период: 2026-06». Это метрики базы данных,
а не рабочего процесса. Ни дедлайна, ни моих заданий, ни просрочек.

**3. Проверяющий не может сверять.** Исполнитель заполняет форму, где строки = каскад P&L,
колонки = площадки. Проверяющий в модалке «Данные» (`process/[id].vue:80`) и на вкладке
«План · Тактика» видит **плоский список** `ЦФО / статья / факт / стратегия / тактика`,
отсортированный по коду ЦФО. Это другая структура, другой порядок строк, без секций и итогов.
Сверить с формой исполнителя физически неудобно — а это основная работа согласующего.

**4. Состояние плана размазано по трём местам.** Прогресс этапов — на карточке;
статусы заданий — в кокпите; сроки (`due_at`) считаются в `calendar.go`, но нигде не
превращаются в «просрочено / осталось 1 день»; блокировки WF-DEP видны только как замочек
на плитке этапа. Нигде нет одной строки «где сейчас план и что его тормозит».

**5. Два словаря статусов с разными значениями.**
Этап: `pending / in_progress / completed / returned`. Задание: `pending / in_progress /
review / done / returned`. Разные слова для одного смысла (`completed` vs `done`), одинаковый
визуал. Пользователь вынужден держать в голове две шкалы.

**6. Делегирование «плоское».** Делегировать можно только задание целиком, через модалку с
поиском по фамилии. Нельзя: отдать одну площадку из четырёх, поставить срок, оставить
комментарий, увидеть историю «кто кому и когда». Уведомления при назначении не уходят —
`internal/plans/` вообще не подключён к `internal/notifications/` (проверено grep'ом),
хотя канал B24 в кабинете уже работает.

**7. Форма перегружена без иерархии.** ~30 строк каскада × N площадок, всё одним полотном,
все ячейки визуально равнозначны. Ввод (5–12 строк) и расчёт (18+ строк) различаются только
бледностью текста. Легенда есть, но она вверху и не липкая.

## 2. Целевая информационная архитектура

Свести всё к **трём уровням** и одному правилу: «период → срез → ячейка».

```
/plans                        РАБОЧИЙ СТОЛ
                              · «Ваши действия»: мои задания с дедлайном и CTA
                              · состояние активного периода одной строкой
                              · список периодов (компактно, для админа)

/plans/[id]                   КАРТОЧКА ПЕРИОДА  (единственная точка по периоду)
   вкладки:
     Обзор                    статус-бар + этапы + блокеры + мои действия
     Свод              ← НОВОЕ, главный экран проверяющего (§3)
     Задания                  бывший кокпит /plans/process/[id]
     Свод по ЮЛ               TPL-08 (как сейчас)
     История                  комментарии + аудит по периоду

/plans/[id]/form?task=NN      ФОРМА ВВОДА (бывш. /plans/mp-form/[taskId])
                              тот же грид, что и на «Своде», в режиме edit
```

Удаляем: `/plans/process/[id]` (переезжает во вкладку «Задания»), `/plans/mp.vue`
(факт становится колонкой/фильтром на «Своде»), `/plans/tasks` в режиме «Все»
(дублирует вкладку «Задания»; режим «Мои» переезжает на рабочий стол).

Правило, которое лечит п.1 и п.5 одновременно: **форма и свод — один и тот же компонент
в двух режимах.** Проверяющий видит ровно те строки, в том же порядке и с той же
группировкой, что видел заполняющий. Разница только в том, что у него нет инпутов
и нет ограничения по ЦФО.

## 3. Экран «Свод периода» — общий просмотр (п.1, п.5, п.6.1–6.3)

Это ключевая недостающая вещь. Одна таблица со всеми данными периода, с фильтрами.

```
┌───────────────────────────────────────────────────────────────────────────────────────┐
│ Тактический план · июль 2026                                          [Экспорт xlsx]  │

│ ── ПРОДАЖИ ─────────────────────────────────────────────────────────────────────────  │

│    ├ Ozon (337)                 310 000      360 000     340 000   −20 000     +9.7%  │
│    │                                                        ⏳ Иванов · в работе      │
│    └ Lamoda (336)               190 000      240 000     230 000   −10 000    +21.1%  │
```

Что здесь решается:

- **п.1** — все данные периода в одном месте, без хождения по заданиям.
- **п.5** — одна форма; ЦФО/площадки — это раскрытие строки, а не отдельные экраны.
- **п.6.1** — фильтры валюты / ЮЛ / large-small прямо в шапке (large-small = сегмент,
  «большие и маленькие МП»).
- **п.6.2** — «детализация по МП по строкам как в шаблоне»: строка-итог блока →
  раскрывается в площадки. Ровно как SPEC §9.5.
- **п.6.3** — колонки «Факт 2025 (тот же месяц)», «Стратегия», «Δ к стратегии»,
  «Δ к факту 25». Набор колонок — переключаемый пресет (SPEC §9.6).
- **проверяющему** — в строке площадки виден исполнитель, статус и метка ручной
  корректировки (✎ с причиной в тултипе; данные уже есть в `pl_adjustment`).
  Клик по значению → drill-down в форму задания.

### API

Один новый эндпоинт вместо латания трёх существующих:

```
GET /api/plans/instances/{id}/board
    ?currency=RUB|BYN|USD
    &legal_entity=Mark+Formelle
    &segment=large|small
    &cfo=335,337
    &country=RU
    &group_by=line|cfo|legal_entity
    &columns=fact_prev_year,strategy,tactic,delta_strategy,delta_fact
→ { period, currency, columns[], groups[ { line: MpLine, total: {...},
      children: [ { code_cfo, name, values{}, task: {id,status,assignee}, is_manual, reason } ] } ] }
```

Собирается из уже готовых кусков: `mpFormSpec()` (структура строк), `TaskStore.Pnl`
(тактика/стратегия/факт из `pl_metric`), `MpFactSource.MpFact(year-1, month)` (факт 2025 —
тот же коннектор, другой год), `convertAmount` (валюта), `dir_cfo.legal_entity` (ЮЛ).
Новой доменной логики почти нет — есть сборка.

Фронт: один компонент `components/plans/MpGrid.vue`:

```
<MpGrid :spec="lines" :data="rows" mode="review|edit"
        layout="rows|columns" :columns="preset" :currency="cur" />
```
`mode="edit"` + `layout="columns"` = текущая форма ввода (её вёрстку переносим как есть),
`mode="review"` + `layout="rows"` = свод. Один источник правды по составу и порядку строк —
`mpform_spec.go`, он уже такой единый источник на бэке.

## 4. Наглядность: «зашёл и понял, что делать» (п.2, п.4)

### 4.1. Статус-бар периода — один компонент на всех экранах

```
июль 2026 · Этап 1.1 «Заполнение бюджетов продаж» · дедлайн 03.07 · ⚠ осталось 1 день
████████████░░░░░░ 67% · заданий 12/18 · ячеек 840/1 240 · просрочено 2 · заблокировано 1
```
Дедлайн уже считается (`businessDayDate` по календарю страны исполнителя) — надо только
довести до UI и добавить производные состояния «просрочено» / «горит сегодня».
Прогресс считать **и по заданиям, и по данным** (сколько обязательных ячеек заполнено из
`mpFormSpec().Editable × площадки`) — «12/18 заданий» без «840/1240 ячеек» врёт: задание
может быть «в работе» с одной заполненной ячейкой.

### 4.2. Единый словарь состояний

Свести этапы и задания к одной шкале с одним цветом и одной иконкой (легенда — в статус-баре):

| Состояние | Цвет | Значение |
|---|---|---|
| Не начато | серый | никто не открывал |
| В работе | синий | исполнитель начал |
| На проверке | жёлтый | сдано, ждёт приёмки |
| Готово | зелёный | принято/согласовано |
| Возвращено | красный | вернули на доработку, есть причина |
| Заблокировано | серый + 🔒 | ждёт зависимость (WF-DEP), с подписью «ждёт этап 2.4» |
| Просрочено | красная рамка | `due_at < сегодня` и не готово |

Переименовать `completed` → `done` в UI-слое (в БД можно оставить), чтобы слово было одно.

### 4.3. Блок «Ваши действия» на рабочем столе

Вместо KPI-плиток базы — персональный чек-лист, отсортированный по «горит»:

```
Сейчас от вас ждут:
  🔴 Бюджет продаж · МП large (4 площадки)      дедлайн сегодня   [Заполнить]
  🟡 Согласовать: МП small · Левин              сдано вчера       [Проверить]
  ⚪ Бюджет расходов · IT                        дедлайн 07.07     [Заполнить]
Вы делегировали:
  · МП small → Качановская, до 03.07 · в работе                   [Напомнить]
```

### 4.4. Пустые состояния и подсказки

Сейчас пустой кокпит показывает «Заданий нет. Нажмите "Генерировать задания"» — это
хорошо, надо так везде: пустой свод → «Данных нет: задания этапа 1.1 ещё не заполнены,
2 из 4 в работе → [Открыть задания]». Каждое пустое место должно называть причину и
следующий шаг.

### 4.5. Форма: иерархия вместо полотна

- Липкая шапка с колонками площадок + липкая первая колонка (частично есть).
- Секции (`Продажи`, `Себестоимость`, …) — сворачиваемые, с итогом в свёрнутом виде.
- Визуально разделить: **ввод** — белый инпут с рамкой; **правка расчёта** (%СПП, наценка) —
  инпут с пунктиром и иконкой формулы; **расчёт** — без рамки, приглушённый. Сейчас это
  различается только цветом текста.
- «Показать только строки ввода» — тумблер (сворачивает 18 расчётных строк из 30).
- Ввод процентов — в процентах (`31`), а не в долях (`0.31`), с суффиксом `%` в поле.

## 5. Назначение и делегирование (п.3)

Цель: назначить кого угодно на что угодно за два клика, и чтобы это было видно всем.

### 5.1. Экран «Ответственные периода» (вкладка «Задания» → режим «матрица»)

```
                    1.1 ввод      1.2 согл.     1.5 расходы
МП large (335,336,337,954)  Мурашко ✓    Ворончук      —
МП small (11 площадок)      ⚠ не назначен Левин        —
Розница РБ                  Смолер       Смолер        Антипова
```
Красная подсветка «не назначен» — сразу видно дыры до старта периода. Массовое назначение
выделением ячеек. Данные уже есть (`pl_task.assignee_user_id`, `plans_deputy`, `jobpos→cfo`).

### 5.2. Разделение задания по площадкам

Сейчас задание «МП large» = 4 площадки одному человеку целиком. Нужно:
`POST /api/plans/tasks/{id}/split {cfo_codes: [337], assignee_user_id: 42}` — из задания
выделяется дочернее по подмножеству ЦФО, с собственным исполнителем и статусом. Родитель
считается готовым, когда готовы все дети. Это и есть «делегировать конкретное задание».

### 5.3. Делегирование с контекстом

Расширить `action=delegate` до `{user_id, due_at, note}`:
- срок делегирования (по умолчанию = дедлайн этапа минус 1 р.д.);
- комментарий «что именно сделать»;
- уведомление делегату (B24 + колокольчик) — **подключить `internal/plans` к
  `internal/notifications`**, сейчас связи нет;
- в карточке задания — цепочка `Мурашко → делегировал Иванову (до 03.07) → сдано → принято`,
  чтобы «кто реально заполнил» было видно без раскопок (частично уже есть — `filledBy`).

### 5.4. Заместители

`plans_deputy` + `users.absence_status` уже реализованы, но в UI не видны. Показывать
бейдж «замещает Мурашко (отпуск до 05.07)» рядом с исполнителем и авто-подставлять
зама при генерации заданий, если основной отсутствует.

### 5.5. Приёмка для проверяющего

Проверяющему нужен не только статус, но и «что изменилось»: в его карточке задания —
diff «стратегия → тактика» по ключевым строкам + все ручные корректировки с причинами
в одном списке (данные в `pl_adjustment` есть, UI нет). Действия «Принять / Вернуть»
с обязательной причиной при возврате (частично есть на этапах, нет на заданиях).

| 3 | Сравнение с фактом 25 и бюджетом (стратегией) | колонки `Факт 07.25 / Стратегия / Δ / Δ%`; факт прошлого года — `MpFact(year−1, month)` | §3, SPEC §9.6 |

## 8. Что важно не сломать

- `mpform_spec.go` остаётся **единственным источником** состава и порядка строк —
  и форма, и свод, и экспорт читают его.
- ABAC (`abac.go`) проверяется на сервере и для свода тоже: проверяющий видит
  свой срез; «все ЦФО» — только по роли.
- Дизайн-система: цвета/радиусы только токенами, числа `--font-mono` + `tabular-nums`
  (SPEC §14.3).
- Обязательность причины при ручной корректировке (ADJ-02) — не ослаблять при
  переезде формы на новый компонент; тесты на это есть.
- Перед коммитом Go: `cd go && go build ./... && go vet ./... && go test ./...`.
