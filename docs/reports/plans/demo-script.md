# Демонстрация «Тактических планов» на проде — сценарий по шагам

Документ отвечает на два вопроса: **что показывать заказчику** и **что для этого
должно быть настроено**. Порядок шагов совпадает с порядком процесса, поэтому его
можно вести как есть, сверху вниз.

Термины, которые нужно различать, иначе демо рассыпается:

| Понятие | Что это | Где живёт |
|---|---|---|
| **Период** (`pl_instance`) | месяц планирования | `/plans` → выбор периода |
| **Этап** (`pl_stage_instance`, 1.1 … 4) | срок и факт прохождения по схеме ТЗ; календарь периода | таймлайн на `/plans/{id}` |
| **Задание** (`pl_task`) | кому что ЗАПОЛНИТЬ; раскрывается только на этапах ввода | кокпит `/plans/process/{id}` |
| **Карточка формы** (`form_card`) | маршрут КОНКРЕТНОЙ формы: заполнение → согласования → утверждение → публикация | блок «Формы периода» на `/plans/{id}`, кнопка «Согласование» |

Ключевое: **согласование идёт по карточкам форм, а не по заданиям.** Задания
существуют только для этапов ввода (1.1, 1.5, 2.1, 2.3 и согласование ЮЛ на
этапе 3). На этапах 1.2/1.3/1.4 заданий нет по дизайну — там согласуются
карточки, у каждой свой лист согласования, своя версия и свой возврат.

## 0. Подготовка (до демо, один раз)

1. **Роли пользователям** — `/admin/users`: `ROLE_PLANS_USER` участникам,
   `ROLE_PLANS_ADMIN` тому, кто ведёт демо (админ процессов видит все срезы и
   умеет переоткрывать период).
2. **Права-срезы** — `/plans/admin/users`: кому какие страна / ЮЛ / шаг / ЦФО
   доступны. Без правил пользователь не видит ни карточек, ни строк: это ABAC, а
   не «забыли включить».
3. **Владельцы шагов** — `/plans/admin/positions` и `/plans/admin/route`:
   должности ЦФО и ответственные по этапам. От владельца шага зависит, кому
   уйдёт уведомление «форма ждёт согласования».
4. **Маршрут формы** — `/plans/admin/form-route`: включён ли шаг «Финансист»,
   работает ли `skip_if_same_user`. Здесь же видно, на каком шаге публикация.
5. **Справочники** — `/plans/directories`: ЦФО, статьи PL (нормативный НДС),
   курсы, состав розницы, сценарии, ЮЛ с УНП. Синхронизация — кнопкой.
6. **Снимок факта МП** — `POST /api/plans/admin/mp-fact-snapshot` (или дождаться
   регламента). Без снимка колонки факта пусты, и это честно написано в шапке
   формы: «снимок факта за период ещё не собран».
7. **Публикация**: `PLANS_PUBLISH_ENABLED=1` для записи в Budgeting, либо
   `PLANS_PUBLISH_SANDBOX=1` для демонстрации записи «без Budgeting» (в отчёте и
   в карточке будет пометка «ПЕСОЧНИЦА»).

### Сброс перед повторным демо

Если период уже «походил» и нужно начать с чистого листа:

```bash
cd swarm
make plans-reset                      # все периоды: задания, карточки, значения
make plans-reset-period Y=2026 M=9    # только один период
```

Удаляется всё, что каскадно висит на `pl_instance` (задания и их история, карточки
с листом согласования и версиями, журнал публикаций, ячейки розницы, значения и
условия МП, этапы). **Остаются** справочники, права-срезы, соответствия
«пользователь ↔ РМ», должности ЦФО и снимок факта МП — то есть настройка, которую
не нужно делать заново.

На проде того же добиваются одним запросом (контейнер PG называется иначе):

```bash
# один период
psql "$POSTGRES_URL" -c "DELETE FROM pl_instance WHERE period_year=2026 AND period_month=9"

# все периоды планов
psql "$POSTGRES_URL" -c "DELETE FROM pl_instance WHERE id > 0"
```

`WHERE id > 0` здесь не лишний: по смыслу это «все строки», но GUI-клиенты
(DataGrip, DBeaver) отклоняют `DELETE` без `WHERE` как unsafe query — с условием
команда одинаково работает и в psql, и в клиенте.

## 1. Старт периода (админ процессов)

1. `/plans` → **создать период** (год, месяц). Создаются этапы со сроками по
   производственному календарю страны и карточки форм по реестру.
2. `/plans/process/{id}` → **«Генерировать задания»**. Задания появляются на
   этапах ввода. Задания «· исполнитель не назначен» — это ЦФО без должности-
   владельца: назначьте исполнителя тут же, кнопкой «Исполнитель».
3. Что показать словами: «этапы — это календарь и сроки, задания — кому
   заполнять, карточки форм — что и кем согласуется».

## 2. Заполнение (роль: заполняющий — РМ, менеджер МП)

Розница:
1. `/plans/{id}` → блок «Формы периода» → **«Форма»** у нужной страны (либо из
   кокпита — задание «Товарооборот розницы · РБ»).
2. Показать: ввод по магазинам и месяцам, подсказки, массовые операции с
   обязательным предпросмотром diff, перенос и сортировку столбцов, LFL-статус и
   его переопределение финансистом.
3. **«Свод»** (`/plans/retail-summary/{cardId}`) — 11 показателей, разрезы
   LFL/новые/закрытые, контрольные сверки (все четыре должны быть по нулю) и лист
   «результат ввода в BYN» — вся структура PL.

Маркетплейсы:
1. `/plans/mp-conditions/{cardId}` — **условия площадки**: %СПП (поле ввода с
   подсказкой «фактическое значение»), наценки, доли статей. Копирование из
   прошлого периода одной кнопкой, diff изменений — согласующему.
2. `/plans/mp-form/{taskId}` — форма: каскад считается из условий (режим
   «расчёт от условий»), суммы можно переопределить руками — видно «расчёт даёт
   X, вручную Y».
3. В шапке — отметка «данные факта актуальны на …»: показать, что факт берётся из
   снимка, а не читается вживую.

## 3. Отправка на согласование (заполняющий)

1. На карточке формы → **«Согласование»** → «Отправить на согласование».
2. Валидации: блокирующие не дают отправить, предупреждающие требуют
   обоснования. Показать на живом примере — это ответ на вопрос «а что мешает
   отправить».
3. После отправки: карточка `on_approval`, шаг 1.2; владельцу шага уходит
   уведомление (колокольчик + Bitrix, если канал включён).

## 4. Согласование руководителем (роль: 1.2) и директором (1.3)

1. Согласующий открывает `/plans/{id}` → карточка формы → **«Согласование»**.
2. Что он видит и что именно согласовывает:
   - **лист согласования** — кто и когда что решил (аннулированные решения после
     возврата остаются видимыми);
   - **версии** — снимок значений на каждый переход, diff «что изменилось»;
   - **форму и свод** (ссылки рядом) — сами цифры;
   - **предпросмотр публикации** — что и куда уедет, без записи.
3. Действия: **«Согласовать»** (двигает на следующий шаг) или **«Вернуть»**
   (только назад, только с комментарием; решения от целевого шага и выше
   помечаются аннулированными). Возврат уведомляет того, кому исправлять.
4. На таймлайне этап 1.2 показывает не «0/0 заданий», а сколько форм ждёт
   решения: клик по плитке объясняет, что согласуются карточки.

## 5. Финальное утверждение и публикация (роль: 1.4 / админ)

1. **«Согласовать»** на шаге 1.4 → карточка `approved`, период закрыт на запись,
   пишется версия-снимок.
2. Если на шаге включена публикация — строки уходят в приёмник тактики
   (`Budgeting.dbo.VFORMTOLOADTAKTTARGET`): DELETE по логическому ключу + INSERT в
   одной транзакции, «Компания» = реальный УНП страны.
3. **Что показать после публикации** (это и есть ответ «опубликовал — и что
   дальше»): вкладка **«Публикации»** в панели карточки — когда, куда, сколько
   строк, сколько записано, расхождение (обязано быть 0) и текст ошибки, если
   что-то не сошлось. Повторная публикация той же версии не удваивает данные —
   идемпотентность по (карточка, версия, приёмник).
4. Изменить утверждённое можно только через **«Переоткрыть период»** с причиной
   (админ процессов); причина уходит в аудит.

## 6. Что показать «на сдачу»

- `/plans/audit` — журнал действий (кто, что, когда).
- `/plans/admin/users` — «кто кого замещает» и срезы доступа.
- Колокольчик — уведомления по заданиям и по карточкам.
- Возврат с 1.3 на 1.1 и повторный проход — самый убедительный сюжет: видно, что
  решения аннулируются, версия растёт, а публикация не дублируется.

## Частые вопросы на демо

**«Я админ — опубликовал, и что дальше?»** Дальше строки лежат в приёмнике
Budgeting, и это видно во вкладке «Публикации» (когда, куда, сколько, расхождение
0). Карточка получает статус «опубликовано» и закрывается на запись. Если включена
песочница (`PLANS_PUBLISH_SANDBOX=1`), в отчёте будет пометка «ПЕСОЧНИЦА» — запись
шла в PG, а не в Budgeting.

**«Почему на 1.2 нет заданий?»** Потому что согласуются карточки форм, а не
задания. Единица маршрута — форма (ТЗ §2.2): возврат мелких МП не должен
останавливать крупные, а возврат одной страны розницы — три остальные.

**«Всё завязано на конкретных пользователях?»** Да: видимость и права — ABAC-срезы
(страна / ЮЛ / шаг / ЦФО), исполнитель задания — должность-владелец ЦФО,
согласующий шага — владелец шага из маршрута. Админ процессов видит всё и может
переоткрыть период. Поэтому для демо под одним пользователем удобнее роль
`ROLE_PLANS_ADMIN`: иначе часть экранов будет пустой — не из-за ошибки, а из-за
среза доступа.

**«Данные задания пустые, хотя форма заполнена»** — так было до 04.09.2026:
модалка читала только слой МП (`pl_metric`), а розница хранит значения в своём
слое (`tp_value`). Исправлено: для розницы показываются суммы периода по
магазинам и метрикам (план продаж, ФОТ, аренда 54/55).
