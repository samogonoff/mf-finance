# Сквозное ревью процесса — по роли и по шагу (04.09.2026)

Ревью после прогона процесса заказчиком. Проверялось не «работает ли кнопка», а
**согласованность процесса**: одно и то же состояние должно одинаково читаться из
таймлайна этапов, из кокпита заданий и из карточки формы.

Проверка сквозная: `TestProcessFlow_PG` (гейт `PLANS_TEST_PG_DSN`) прогоняет
период целиком — карточки → отправка → возврат → повторный проход → утверждение →
переоткрытие, и на каждом шаге сверяет ЭТАП, ЗАДАНИЕ и КАРТОЧКУ между собой.

## Что было не так (и что стало)

| № | Расхождение | Как проявлялось | Исправлено |
|---|---|---|---|
| 1 | Этап, задание и карточка двигались независимо | «Этап 1.2 готово» при формах в черновиках; задание «готово» при пустой форме | Этапы 1.1–1.4 стали агрегатом карточек; ручное закрытие такого этапа отклоняется с перечнем непрошедших форм |
| 2 | Задание не знало о форме | Форму отправили — задание висит «в работе» | Задание закрывается отправкой формы, возвращается вместе с ней |
| 3 | `skip_if_same_user` при НЕназначенном владельце | Форма молча проскакивала руководителя, в листе «согласовано автоматически» без человека | Пропуск только при реальном совпадении отправителя и согласующего |
| 4 | Отправка не проверялась на сервере | Форму можно было отправить мимо валидаций — согласующий обязан вернуть, лишний круг | Гейт на submit: 422 с перечнем причин; недоступность проверки не блокирует |
| 5 | «Данные» задания читали только слой МП | У розницы модалка пуста на заполненной форме | Слой выбирается по form_code; для розницы — суммы периода по магазинам и метрикам |
| 6 | Согласование не уведомляло | Форма ушла на 1.2, руководитель не знает | Уведомления на submit/approve/return/reopen; возврат уведомляет и владельца шага, и автора |
| 7 | Карточки создавались при первом открытии экрана | После старта периода «формы не созданы», этапы в pending | Карточки заводятся вместе с периодом |
| 8 | Роль финансиста = только админ | На включённом шаге «Финансист» его владелец мог согласовать, но не мог править LFL и расчётные статьи | Финансист — админ ИЛИ явное право на шаг `fin` в срезах |
| 9 | Форму МП мог открыть любой пользователь по номеру задания | Обход ABAC-срезов, ради которых РМ не видит чужие площадки | Чтение проверяется по срезу: доступ, если хотя бы один ЦФО задания в нём. Срез не настроен — не запрещаем (иначе регресс, а не защита) |
| 10 | Экспорт формы МП тоже шёл без проверки среза | ABAC обходился выгрузкой файла | Экспорт проверяет доступ так же, как чтение |
| 11 | Кнопка «Согласовать» на этапе 1.х | Сервер её теперь отклоняет, а интерфейс предлагал — человек считал, что двигает процесс | Для этапов, которыми управляют карточки, вместо кнопки — переход к формам на решении |

## Роль за ролью

### Заполняющий (РМ розницы, менеджер МП) — шаг 1.1

| Что должен | Состояние |
|---|---|
| Видеть только свои магазины | ✅ соответствие «пользователь ↔ RegManager» (`tp_reg_manager_map`); нет соответствия — видит всё в пределах среза (он не РМ) |
| Вводить только в открытой форме | ✅ ввод разрешён в `draft` и `returned`; после отправки форма read-only ДЛЯ ВСЕХ |
| Понимать, что мешает отправить | ✅ блокирующие валидации в форме, и теперь сервер отказывает с перечнем причин |
| Видеть подсказки, а не подставленные значения | ✅ %СПП, штрафы, аренда — поля ввода; факт рядом, с источником и периодом |
| Знать, что форму вернули | ✅ уведомление о возврате (владельцу шага и автору), причина в тексте |
| Не отправлять чужое | ✅ право на шаг и на карточку проверяется по срезам |

### Финансовый контролёр — шаг `fin` (в маршруте выключен, включается данными)

| Что должен | Состояние |
|---|---|
| Переопределять LFL-статус с причиной | ✅ право теперь и у него (явный шаг `fin`), а не только у админа |
| Править расчётные статьи (ФОТ, аренда) | ✅ то же право |
| Согласовать или вернуть | ✅ как обычный шаг маршрута |
| Шаг не должен ломать таймлайн | ✅ своего этапа у `fin` нет: карточка на `fin` считается прошедшей 1.1 и не прошедшей 1.2 |

### Руководитель подразделения (1.2) и директор направления (1.3)

| Что должен | Состояние |
|---|---|
| Узнать, что форма ждёт решения | ✅ уведомление (колокольчик + Bitrix), плитка этапа «N форм ждёт решения» |
| Понять, ЧТО согласовывать | ✅ в попапе этапа — список форм на его шаге; в карточке — лист согласования, версии со снимками, ссылки на форму и свод, предпросмотр публикации |
| Видеть цифры целиком, а не свой срез | ✅ отчёт валидаций и свод считаются по всем строкам экземпляра |
| Вернуть только назад и только с причиной | ✅ проверяется в маршруте; решения от целевого шага и выше помечаются аннулированными (не удаляются) |
| Не иметь возможности «закрыть этап» вместо решения | ✅ ручное закрытие этапа 1.х отклоняется с перечнем форм |

### Финальное утверждение (1.4)

| Что должен | Состояние |
|---|---|
| Утвердить и закрыть период на запись | ✅ `approved` + `locked`, версия-снимок |
| Опубликовать во внешний контур | ✅ на шаге с `publish_on_approve`; DELETE+INSERT в транзакции, «Компания» = реальный УНП |
| Увидеть результат публикации | ✅ вкладка «Публикации»: когда, куда, сколько строк, расхождение, ошибка |
| Не удвоить данные повторной публикацией | ✅ идемпотентность по (карточка, версия, приёмник) |

### Администратор процессов

| Что должен | Состояние |
|---|---|
| Создать период | ✅ вместе с ним создаются этапы, карточки форм; задания — кнопкой |
| Назначить исполнителей и владельцев шагов | ✅ кокпит процесса; задания «исполнитель не назначен» видны отдельно |
| Настроить маршрут формы и права-срезы | ✅ `/plans/admin/form-route`, `/plans/admin/users` |
| Переоткрыть утверждённый период | ✅ только с причиной, причина в аудит; таймлайн откатывается |
| Записать план в приёмник | ✅ запись — админ; предпросмотр доступен согласующему |
| Видеть всё | ✅ админ обходит срезы |

### Наблюдатель (BI, руководство)

Отдельной роли «только чтение» нет: доступ даётся правами-срезами с `ROLE_PLANS_USER`.
Это осознанно — в ТЗ такой роли нет, а «видит, но не действует» получается срезом
без прав на шаги. Если понадобится — добавляется правилом, а не кодом.

## Шаг за шагом: что проверено сквозным прогоном

1. **Старт периода.** Создаются этапы (сроки по календарю страны) и карточки форм.
   Этапы согласования при черновиках НЕ завершены.
2. **Отправка одной формы.** Карточка уходит с шага заполнения; этап 1.1 —
   `in_progress` (остальные формы не отправлены); задание своей страны — `done`,
   задания других стран не тронуты.
3. **Возврат руководителем.** Карточка `returned` на 1.1; этап 1.1 — `returned`
   (возврат виден на таймлайне); задание вернулось в работу.
4. **Повторный проход всех форм до утверждения.** Этапы 1.1–1.4 — `completed`;
   этап производства не тронут (карточками не управляется); все задания
   заполнения закрыты.
5. **Закрытый период.** Утверждённая карточка `locked`; повторная отправка
   отклоняется; `reopen` без причины отклоняется, с причиной — открывает форму и
   откатывает таймлайн.

## Осталось (не блокирует демо)

1. **Публикация розницы включена только по BY** — для RU/KZ/UZ нет подтверждённого
   КодPL (ждём BI). Видно в отчёте dry-run как «ожидает подтверждения».
2. **Этапы производства (2.x), расходов (1.5), свода (1.6) и ЮЛ (3, 4)** двигаются
   вручную: форм под них ещё нет. Когда появятся — они автоматически попадут в тот
   же агрегат (достаточно завести карточки и шаги маршрута).
3. **Роль «только чтение»** — если заказчик попросит, это правило в срезах, а не код.
