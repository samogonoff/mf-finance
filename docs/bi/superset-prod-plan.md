# Superset на проде: архитектура встраивания и инженерные правила

**Статус: отложено осознанно (решение от 11–12.08.2026).**

Сначала отрабатываем аналитику на dev-контуре: собираем витрины и дашборды,
набиваем руку, определяем метрики. К проду возвращаемся, когда будет что
выкатывать. Этот документ — чтобы не восстанавливать рассуждения заново.

Что уже сделано и работает: `swarm/superset/` (контур, образ, конфиг),
`swarm/superset/assets/` (ассеты в git), `swarm/superset/README.md` (цикл
dev→git→prod для дашбордов), MCP-сервер, скиллы. В `ci-finance.yml` ничего не
добавлено.

## Часть 1. Как встраивать дашборды в кабинет

### Цепочка доверия

Целевая схема: дашборды Superset встраиваются в страницы кабинета, доступы
выдаются на страницы. Ключевой факт, который определяет всю реализацию:

**Superset про Битрикс не знает ничего.** Встроенный дашборд смотрит анонимный
guest-пользователь с ролью из `GUEST_ROLE_NAME`. Учётки финансистов в Superset
не появляются. Битриксовая авторизация работает до этого:

```
пользователь → B24 OAuth → Go-API (токен в Redis, роли из ExpandRoles)
                                  │
                     Nuxt просит guest-токен для дашборда
                                  │
                  Go-API ПРОВЕРЯЕТ сессию и роли ← настоящий гейт
                                  │
              минтит guest token (ресурсы + RLS), подпись GUEST_TOKEN_JWT_SECRET
                                  │
              Superset принимает токен, доверяя подписи
```

Для пользователя это выглядит как «зашёл по Битриксу и видит дашборд», второго
логина нет. Технически Superset доверяет Go-API, а Go-API доверяет Битриксу.

Следствия:

- Заводить или синхронизировать пользователей Superset не нужно.
- Права внутри дашборда — это **содержимое токена** (список ресурсов + RLS),
  а не роли Superset. `Gamma`/`Alpha` к встроенному просмотру не относятся.
- Кто смотрел — Superset знает только из полей токена. Аудит-след придётся
  вести на стороне Go-API (см. ниже), внутри Superset все зрители анонимны.
- `GUEST_TOKEN_JWT_SECRET` живёт в `docker config` рядом с
  `INTERNAL_SERVICE_TOKEN`. Его ротация разом гасит все открытые дашборды.

### Два независимых контура доступа

Их легко спутать, и путаница дорого стоит:

| Кто | Куда | Как авторизуется |
|---|---|---|
| Финансист | страница кабинета с iframe | B24 → Go-API → guest token |
| Аналитик, который строит дашборды | сам Superset UI | отдельно; сейчас локальная учётка |

Прикрутить B24 и ко второму контуру можно (Flask-AppBuilder,
`AUTH_TYPE = AUTH_OAUTH`), но для встраивания это не нужно. Делать только если
дашборды будут строить несколько человек.

### Один реестр дашбордов в git

Главная ошибка, в которую легко попасть, — размазать доступы по трём местам:
роли в Nuxt-миддлваре, embed UUID на фронте, RLS-правила в админке Superset.
Через полгода они разъедутся, и никто не ответит, кто что видит.

Решение — реестр в коде, один на всё:

```go
// go/internal/bi/registry.go
type Dashboard struct {
    Slug         string    // "cost-margin" — то, что знает фронт
    EmbedUUID    string    // UUID из Superset; фронт его НЕ видит
    RequiredRole string    // ROLE_COST_USER
    ScopeBy      ScopeKind // none | cfo | level01 — как строить RLS
}
```

Из него растут ровно две вещи:

- `GET /api/bi/dashboards` → что этот пользователь вправе видеть. Кормит и меню,
  и `nuxt/middleware/scope-guard.ts`. Список ролей больше нигде не дублируется.
- `POST /api/bi/guest-token` → сам токен.

Реестр в git, а не в БД: это часть контракта доступов, она должна проходить ревью
в MR вместе с `swarm/superset/assets/dashboards/*.yaml`. Пара «slug ↔ embed UUID»
связывает два git-дерева, и рассинхрон виден глазами.

### Контракт эндпоинта

```
POST /api/bi/guest-token   { "slug": "cost-margin" }
```

**Фронт передаёт slug, а не embed UUID.** Это не косметика: если клиент
присылает UUID, он попросит токен на любой дашборд, и гейт становится
декорацией. Неизвестный slug — 404.

Внутри три шага в этом порядке:

1. Проверить сессию (обычный auth middleware) и `RequiredRole` через
   существующий `ExpandRoles`.
2. Построить RLS из **существующего ABAC**. В `plans/abac.go` и
   `plans_user_scope` уже живёт логика «какие ЦФО видит пользователь». Нужен
   адаптер, а не вторая реализация прав: два источника истины о правах — это
   гарантированный инцидент.
3. Запросить у Superset guest token, вернуть фронту вместе с TTL.

Логировать каждую выдачу: кто, какой дашборд, когда. Это единственный аудит-след.

### Пакет, фронт, сеть

**Новый пакет `go/internal/bi/`**, а не догрузка в `auth/`. Своя
ответственность (посредник к Superset), свой конфиг, свои тесты. Тесты здесь
естественные и нужны: маппинг slug→UUID, отказ на недостаточной роли,
построение RLS по скоупу — чистые функции, живой БД не требуют, как в
`internal/plans/`.

**Фронт: один composable `nuxt/composables/useSupersetEmbed.ts`**, а не
копипаста на каждой странице. Получает токен, монтирует через
`@superset-ui/embedded-sdk`, перевыпускает по таймеру на TTL/2. TTL
guest-токена — 5 минут (`GUEST_TOKEN_JWT_EXP_SECONDS`), без refresh дашборд
отвалится у любого, кто открыл страницу и отошёл. Токен держать **в памяти**,
не в `localStorage`: это bearer к финансовым данным.

**Сеть: nginx-фасад, не прокси через Go.** Superset должен быть доступен
браузеру пользователя — iframe грузится клиентом, это неизбежно. Отсюда:

- Отдельный хост (`bi.finance.local` в dev, свой домен в прод) на фасаде —
  симметрично тому, как `api.finance.local` отделён от `finance.local`.
- `TALISMAN_ENABLED=1` в прод, `frame-ancestors` = домен кабинета. Без этого
  браузер заблокирует iframe.
- Прямой доступ к UI Superset (`/login`, SQL Lab) закрыть на фасаде, оставить
  только из внутренней сети. Аналитики ходят через VPN.

Проксировать Superset через Go-API **не надо**: соблазн «один контур
авторизации» стоит сломанного SDK, статики и постраничных редиректов.

## Часть 2. Инженерные правила

Первые два важнее всей остальной инженерии.

### 2.1. Одно число считается в одном месте

Самый серьёзный риск не технический. В кабинете **уже** есть отчёты, которые Go
считает сам (`internal/reports/debt`, `internal/plans/calc.go`). Superset умеет
считать то же самое своими виртуальными датасетами. Через месяц-два ВГО-отчёт и
дашборд по ВГО разойдутся на 200 рублей — и доверие потеряет весь кабинет, не
только дашборд.

**Правило: если число показывается и в кабинете, и в Superset, оно считается
один раз.** Место расчёта — ClickHouse (есть `clickhouse/migrations/`, цепочка
миграций, ETL). Go-API и Superset оба становятся читателями одной витрины.

Виртуальные датасеты Superset — только для того, что нигде больше не
используется: разведка, одноразовая аналитика, черновики.

**Контрактный тест в CI:** одна метрика, два пути (`GET /api/reports/debt/...`
и `POST /api/v1/chart/data`), проверка совпадения сумм. Тест дешёвый, ловит
расхождение до того, как его найдёт финансист. Этой болью проект уже жил —
сверка методов `findebt` vs `findebt-docdate`.

### 2.2. Словарь метрик — до первого чарта

Финансовый BI умирает не от техники, а от того, что «маржа» у трёх человек
считается по-разному, и каждый строит свой дашборд.

`docs/bi/metrics.md`: на каждую метрику формула, источник, владелец и что она
**не** включает. До того, как нарисован первый чарт. Без словаря через полгода
будет двадцать дашбордов, из которых никто не рискнёт удалить ни один, потому
что непонятно, чем они отличаются.

Проект к этому особенно склонен: уже есть три методики по задолженности
(`mssql` / `finpl` / `glmf`) и явное правило не переключать дефолт до сверки
чисел. Та же дисциплина нужна в BI.

### 2.3. Прод — артефакт сборки, а не место работы

Раз дашборды в git, довести до конца: **на проде дашборды руками не правят.**

- Админский пароль на проде — в `docker config`, не раздаётся. Пользователи `Gamma`.
- Единственный, кто пишет в прод-метабазу, — CI, через `assets_sync.py import`.
- **Drift-detection в CI:** экспортировать с прода и сравнить с git-деревом.
  Расхождение = кто-то правил в UI, пайплайн падает. Иначе через квартал прод и
  git разъедутся молча, и следующий импорт затрёт чью-то работу.

Это же даёт бесплатный staging: ветки `stage` / `master` уже есть, дашборды
поедут тем же маршрутом, что код.

### 2.4. Штамп свежести на каждом дашборде

Дашборд по ClickHouse-фактам врёт, если ETL не отработал ночью, и врёт **молча** —
цифры выглядят правдоподобно.

Обязательный элемент каждого дашборда: `max(DateOfLoad)` из источника, в шапке.
Дешёвый header-чарт, снимает целый класс вопросов «почему не сходится с 1С» —
потому что данные на позавчера. В финансах пользователь всегда должен видеть,
**на какой момент** данные.

### 2.5. RLS: атрибуты пользователя, а не генерация клауз

Два способа, и второй чище:

- Go строит SQL-клаузу (`cfo_code IN (...)`) и кладёт в токен. Гибко, но логика
  прав уезжает в Go-код и в git-ассетах её не видно.
- Go кладёт в токен **атрибуты** (`cfo_codes: [...]`), а в Superset лежит **одно**
  RLS-правило, использующее их через Jinja. Правило живёт в git как ассет,
  ревьюится, видно глазами.

Рекомендация — второй. **Но перед выбором проверить на нашей версии**, что Jinja
в RLS работает с атрибутами guest-токена: вокруг этого в Superset были регрессии
между 4.x и 5.x. Проверка на пять минут, решение архитектурное, откатывать
больно.

### 2.6. MCP — только dev

Агент через MCP собирает черновик дашборда за минуты. Полезно ровно до того
момента, как кто-то подключит MCP к проду.

- MCP-эндпоинт **не поднимается** в прод-стеке. Не «закрыт авторизацией» — не существует.
- Всё, что агент собрал на dev, проходит `export` → `git diff` → ревью. Diff и
  есть ревью, ради этого весь git-контур и строился.
- Побочный эффект: агентские дашборды не отличаются по процессу от рукописных, и
  не нужно отдельно решать, доверять им или нет.

## Часть 3. Порядок работ

Соблазн начать с embedding, потому что он интереснее. Так нельзя:
**RLS применяется к колонкам датасета.** Если сначала построить витрины, а потом
прикручивать скоупинг, окажется, что в витрине нет `cfo_code` — и переделывать
придётся датасеты, чарты и дашборды.

1. **Витрины с ключом скоупинга сразу.** Проектируя датасет, закладывать колонку,
   по которой потом будет резать RLS (`cfo_code`, `level01` — что применимо).
   Даже если сейчас все видят всё.
2. Один дашборд целиком, до конца: экспорт в git, `git diff`, коммит. Прогнать
   цикл хотя бы раз на живом примере.
3. **Тема Superset под дизайн-систему**, коммитом в git (тема — такой же ассет,
   со своим `/api/v1/theme/import/`). До embedding: иначе первый встроенный
   дашборд будет выглядеть чужеродно, и это увидит заказчик.
4. `go/internal/bi/` + реестр + эндпоинты, с тестами.
5. `useSupersetEmbed` и первая страница.
6. RLS включить последним — когда есть на чём проверить, что срез реально режет.

## Часть 4. Чего не делать

- Не выключать `WTF_CSRF_ENABLED` глобально (совет, который гуляет по интернету).
  Точечный exempt для эндпоинта guest-токена.
- Не заводить и не синхронизировать пользователей Superset из B24.
- Не отдавать фронту embed UUID и тем более не давать ему влиять на RLS.
- Не проксировать Superset через Go-API.
- Не поднимать MCP в прод-стеке.

## Часть 5. Открытые вопросы

- **Под каким доменом Superset живёт в прод.** DNS + сертификат; от этого
  зависят `frame-ancestors` и настройки фасада.
- Нужен ли B24 OAuth для входа в сам Superset UI (второй контур доступа), или
  достаточно локальных учёток для двух-трёх аналитиков.
- Метабаза Superset на проде — отдельный Postgres (не `finance`). Где именно
  живёт, кто бэкапит.

## Разделение работ: что девопс, что мы

Целевой сценарий: локально разрабатываем и коммитим; когда дашборды готовы —
девопс поднимает инфраструктуру Superset в прод, а наши наработки уезжают туда
обычным мержем. Ниже — кто за что отвечает, чтобы разговор с девопсом был
предметным.

### Девопс (инфраструктура, вне репозитория)

1. Хост и домен для Superset + сертификат. От домена зависит `frame-ancestors`
   в CSP, то есть без него встраивание не настроить.
2. **Метабаза Postgres — отдельный инстанс, с бэкапами.** Это состояние, а не
   приложение: в стеке приложений ей не место (см. мину с SHA-тегами ниже).
   Потеря метабазы = потеря всех дашбордов, которые не выгружены в git.
3. Redis для Superset (свой инстанс либо отдельная БД в существующем).
4. Секреты в CI-переменные (`ENV_FILE`): `SUPERSET_SECRET_KEY`,
   `SUPERSET_ADMIN_PASSWORD`, все `SUPERSET_DB_*_URI`, позже
   `GUEST_TOKEN_JWT_SECRET`.
5. Сетевые доступы: из контейнера Superset до ClickHouse / Postgres / MSSQL;
   из браузера пользователя — до Superset (иначе iframe не загрузится).
6. nginx-фасад: `frame-ancestors` = домен кабинета; `/login` и SQL Lab закрыть
   снаружи, оставить только из внутренней сети для аналитиков.

### Мы (в репозитории, коммитами)

1. `swarm/superset/Dockerfile` — **готов.**
2. Сервисы Superset в `swarm/docker-compose.yml` (prod-stack) — написать.
3. Джобы в `ci-finance.yml`: сборка образа в `publish` + импорт ассетов после
   `deploy` — написать.
4. Сами ассеты: датасеты, чарты, дашборды, тема — этим занимаемся сейчас.
5. `go/internal/bi/` + `useSupersetEmbed` — когда дойдём до встраивания.

### Главное: «накатываем на прод» — это не ручная операция

После того как девопс поднял инфраструктуру, выкатка дашборда = **обычный мерж в
`master`**. CI сам делает `assets_sync.py import`. Никто не заходит в прод-UI и
не перерисовывает дашборды руками — ровно ради этого git-контур и строился
(см. §2.3 «Прод — артефакт сборки»).

### Что спросить у девопса ЗАРАНЕЕ, не дожидаясь готовности дашбордов

Детали (домен, порты, сертификат) можно обсуждать потом. Но один вопрос стоит
задать сразу: **готовы ли вообще держать ещё один сервис с отдельной БД и
бэкапами.** Если ответ «нет ресурса» — вся схема с прод-встраиванием под
вопросом, и лучше узнать это до того, как построено двадцать дашбордов.

### Вероятно более простой вариант, чем Swarm-стек

Superset не обязан жить в том же `docker stack`. Отдельный `docker compose` на
том же хосте:

- снимает мину с SHA-тегами (см. ниже) целиком;
- позволяет обновлять Superset независимо от релизов кабинета — версии BI и
  приложения не обязаны совпадать;
- девопсу проще: обычный compose вместо правки продового стека.

Минус — выкатка Superset выпадает из общего пайплайна и становится отдельной
процедурой. Обсудить с девопсом; на вид плюсы перевешивают.

## Мина в deploy-джобе: все образы стека обязаны иметь тег = SHA коммита

Проверено 12.08.2026 по `swarm/ci-finance.yml`. После `docker stack deploy` идёт
такой цикл:

```bash
for SERVICE in $(docker stack services "$SWARM_SERVICE_NAME" --format '{{.Name}}'); do
  TAG=$(docker service inspect "$SERVICE" --format '...Image' | cut -d: -f2 | cut -d@ -f1)
  if [[ "$TAG" != "$CI_COMMIT_SHORT_SHA" ]]; then FAILED=1; fi
done
```

Он обходит **все** сервисы стека и требует, чтобы у каждого тег образа совпадал
с SHA коммита. Отсюда следствие, которое ломает наивную попытку добавить Superset
в прод:

**Любой новый сервис в prod-стеке обязан собираться своим Dockerfile'ом в job
`publish` и получать тег `$CI_COMMIT_SHORT_SHA`.** Поставить `image:
postgres:16-alpine` или `apache/superset:6.1.0` напрямую нельзя — проверка
свалит весь деплой.

Именно поэтому в репозитории есть `swarm/redis/Dockerfile` — тривиальная обёртка
над официальным образом, существующая ровно для того, чтобы у redis появился
SHA-тег. Для Superset понадобится то же самое: наш `swarm/superset/Dockerfile`
уже подходит (он собирается из `apache/superset`), но метабазе Postgres нужна
будет такая же обёртка, либо метабаза выносится за пределы стека.

Второй вариант, вероятно, правильнее: метабаза Superset — это состояние, её место
не в стеке приложений, а рядом с остальными БД, с бэкапами.

## Что нужно будет добавить в CI

Ничего из этого пока не сделано, схема на будущее:

1. Образ `superset` в job `publish` (из `swarm/superset/Dockerfile`).
2. Сервисы `superset` + `superset-worker` в `docker-compose.yml` (prod-stack
   Swarm), с `%%CONFIG_NAME%%`-конфигом по образцу остальных. **Без** `superset-mcp`.
3. Job после `deploy` — импорт ассетов:
